# Phase 1.6-2 — Backend: Margin Analytics Computation

[← back to Phase 1.6 index](./README.md)

## Objective

Compute profitability from the margin fields [1.6-1](./1.6-1-margin-data-model.md)
adds to the catalog: total margin, an average margin rate, breakdowns by
product/service/client (the "cercles" data source), a monthly trend
alongside revenue, and an optional net-profit-after-charges figure crossed
with Phase 17's existing estimated-charges computation.

## Per-line margin resolution

The core primitive, used by every aggregation below. Resolved **live**
against the current `Product`/`Service` row via `productId`/`serviceId`
(see the track README's non-goals for why this is a live join, not a
snapshot).

**Product line (`InvoiceLine`)** — `product` is `null` (freehand line) or
`product.marginMode` is `null` (not configured) ⇒ unresolved, contributes
`0` to margin and its `lineTotalExclVatCents` goes to
`uncategorizedRevenueExclVatCents` instead. Otherwise:

- `PERCENTAGE`: `round(line.lineTotalExclVatCents * product.marginPercentageBasisPoints / 10_000)`
  — scales naturally with whatever the line actually sold for, including
  waste-surcharge/packaging-rounding adjustments already baked into
  `lineTotalExclVatCents`.
- `NET_AMOUNT`: `round(product.marginAmountCents * Number(line.billedQuantity))`
  — **using `billedQuantity`, not the raw site `quantity`** (a correction
  made during implementation: `billedQuantity` is what waste-surcharge/
  packaging-rounding actually turned into a billed amount, the same basis
  `lineTotalExclVatCents` itself is computed from — using the raw quantity
  instead would have scaled margin off a number that doesn't match what was
  charged). The "3€ sur les 6€" framing is per unit, so it scales with
  billed quantity, not with whatever price the line actually charged.
  **Clamped** to `lineTotalExclVatCents` (`Math.min(...)`) as a defensive
  floor: if the artisan discounted this specific line below the catalog
  price after configuring the margin, the reported margin can never exceed
  what was actually billed, even though nothing re-validates the catalog's
  `marginAmountCents ≤ priceCents` invariant against a since-edited line.

**Service line (`InvoiceServiceLine`)** — same fork, against
`service.marginMode`, applied to `serviceLine.amountCents` (no quantity —
a service line is already a total, not a unit price). Its **margin** is
counted for **both** `visibility` values, `VISIBLE` and `REDISTRIBUTED`
alike — see the track README's scope decision for why this deliberately
doesn't follow `bucketByCategory`'s "`REDISTRIBUTED` folds into the product
lines" treatment; margin answers a different question than
revenue-category bucketing does. Its **revenue is a different story, and
this is the one place the original plan below had a real bug**: a
`REDISTRIBUTED` line's `amountCents` is already folded into the product
lines' own (inflated) `lineTotalExclVatCents` by `InvoiceCalculationService`
(see `InvoiceMapper`'s comment on `InvoiceLineWithTotal.lineTotalExclVatCents`)
— counting it again toward `invoiceRevenueCents`/`totalRevenueExclVatCents`
double-counts the same euros, exactly the double-count
`bucketByCategory`'s own comment explains skipping `REDISTRIBUTED` avoids.
Caught by a dedicated test (`totalRevenueExclVatCents` came back inflated
by the redistributed amount) before shipping. Fixed: a `REDISTRIBUTED`
service line's `amountCents` still feeds `marginByService`'s own row (so
that row's `marginRatePercent` is meaningful) and `invoiceMarginCents`, but
never `invoiceRevenueCents`/`uncategorizedRevenueExclVatCents` — only a
`VISIBLE` service line's revenue is added there.

**`MANUAL` invoices** (`entryMode = MANUAL`) — no catalog lines exist at
all; the whole `subtotalExclVatCents` goes to
`uncategorizedRevenueExclVatCents`, `0` margin — same precedent
`getActivityAnalytics`/`bucketByCategory` already apply to manual rows.

## Two more corrections, found live against the real demo stack (not caught by unit tests)

Live-verifying this phase (see [1.6-3](./1.6-3-margin-stats-frontend.md)'s
own Notes) surfaced two real bugs unit tests missed, both because every
existing fixture happened to sidestep them:

- **`marginCoveragePercent` read 39% with a 0% average margin rate** — an
  incoherent combination, caught on first look at the real "Marge" tab.
  Cause: `findMarginConfigByIds` returns a row for every id it's asked
  about, whether or not that catalog item actually has a margin configured
  (`marginMode: null` is a completely normal row shape) — but the
  "uncategorized" check was `if (!config)`, which only catches "no catalog
  reference at all," not "has a reference but never configured a margin."
  A product that merely *existed* in the catalog was silently counted as
  "covered." Fixed with a `hasMarginConfigured(config)` helper
  (`config != null && config.marginMode != null`), used everywhere the
  uncategorized-revenue check happens. Every unit test's mocked
  `findMarginConfigByIds` either returned nothing for a given id (the
  correctly-handled case) or a fully-configured row — never the
  in-between "row exists, `marginMode` is null" shape a real batch query
  actually returns — which is exactly why this needed live data to
  surface. A regression test now covers it explicitly.
- **`marginByClient` labeled its slice with a raw `customerId` UUID
  instead of a name** — visible immediately on the "Par client" donut.
  Cause: `const clientKey = invoice.customerId ?? invoice.customerName`
  was copied from `getActivityAnalytics`'s *uniqueness-counting* set
  (`clientIds`, which legitimately prefers `customerId`), not from its
  *display* map (`clientTotals`, which `getActivityAnalytics` keys by
  `invoice.customerName` alone, always). Every test fixture in this file
  defaults `customerId: null`, so `?? customerName` always resolved to the
  name in tests — the bug only exists for an invoice tied to a real saved
  `Customer` row, which only the live demo data (seeded with real
  `Customer` links) exercised. Fixed to `invoice.customerName` directly,
  matching `getActivityAnalytics` exactly. A regression test with
  `customerId` set now covers it.

Both are a concrete instance of this app's own "verify live, not just
unit tests" convention actually catching something — see 1.6-3's Notes for
the full live-verification pass these came out of.

## Update (2026-09-03) — default margin is 100%, not "uncategorized"

Requested directly by the user, superseding this doc's original per-line
resolution rules above: **an untouched catalog `Product`/`Service`
(`marginMode` still `null`) now defaults to 100% margin — the whole line
is assumed profit — rather than contributing `0` margin and counting as
uncategorized.** The distinction that actually matters now is not "did the
artisan configure a margin" but "is this revenue tied to a real catalog
object at all":

- **A freehand line, or a `MANUAL` invoice** (no `productId`/`serviceId`
  reference whatsoever) — genuinely nothing to assume, stays `0` margin,
  counted in `uncategorizedRevenueExclVatCents` exactly as before.
- **A real catalog `Product`/`Service`, `marginMode` still `null`** — now
  resolves to `baseAmountCents` (100%) and counts as **covered**, not
  uncategorized. This is the actual behavior change.
- **A real catalog item with an explicit `marginMode`** — unchanged,
  resolves to the artisan's own configured value.

`resolveMarginCents` (`backend/src/common/margin.util.ts`) implements this
with a two-step check — `!config` (no catalog link at all) returns `0`;
`config.marginMode == null` (a real, untouched catalog object) returns
`Math.max(baseAmountCents, 0)` — rather than the original single
`!config || config.marginMode == null` check that treated both cases as
"no margin." `hasMarginConfigured` (`reports.service.ts`) was renamed to
`hasCatalogMarginObject` and simplified to `config != null`, matching the
new "covered = has a catalog link" meaning used for
`uncategorizedRevenueExclVatCents`/`marginCoveragePercent`.

**Informing the artisan**: this optimistic default is only useful if it's
visible as an assumption, not mistaken for a real number — see
[1.6-3](./1.6-3-margin-stats-frontend.md#update-2026-09-03--100-default-tooltip)
for the info tooltip and form hint this update also added.

Tests updated: the previous regression test asserting "untouched catalog
product = uncategorized, 0% coverage" was rewritten to assert the new
correct behavior (100% margin, fully covered) — see
`reports.service.spec.ts`'s `defaults an untouched catalog product to 100%
margin, and counts it as covered` and the sibling freehand-line test that
confirms the old behavior still holds where it should. A new
`margin.util.spec.ts` covers `resolveMarginCents` directly and in
isolation for the first time.

## Non-goals

- **No caching/materialization** — computed on demand from the same
  12-month window every other analytics figure already re-scans live, same
  performance posture as `getActivityAnalytics`.
- **No margin figure on the quarterly report (`getQuarterlyReport`)** —
  that endpoint stays exactly what it is today, a URSSAF declaration aid;
  this is a separate, gated method entirely, same relationship 1.3-6's
  `getEInvoicingSnapshot` has to `getActivityAnalytics`.

## Notes

- The live-join (not snapshot) decision means a company with zero
  configured margins gets `marginCoveragePercent: 0` /
  `uncategorizedRevenueExclVatCents = totalRevenueExclVatCents` for their
  *entire* 12-month window immediately after configuring their first
  product — expected and correct, not a bug: nothing retroactively knows
  what an unconfigured item's margin "would have been."
