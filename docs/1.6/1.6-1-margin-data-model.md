# Phase 1.6-1 — Data Model: Margin Field on Product & Service

[← back to Phase 1.6 index](./README.md)

## Objective

Give every catalog item (`Product`, `Service`) an optional margin/profit
declaration, in the same "paramètres avancés" section the artisan already
uses for `activityCategory`, packaging, code, etc. — exactly where the user
asked for it. Two input modes, chosen per item: a net euro amount ("3€ sur
les 6€") or a percentage of the item's own price ("50% sur les 6€", with a
slider).

## Data model

New enum, `backend/prisma/schema.prisma`, same naming convention as
`ServicePricingMode`:

```prisma
enum MarginMode {
  NET_AMOUNT
  PERCENTAGE
}
```

On both `Product` and `Service`, three new nullable columns (identical
shape on each model — copy, don't share a table, same as how `priceCents`/
`activityCategory` are independently declared on both today):

```prisma
marginMode                  MarginMode?
// HT, per unit for Product (mirrors priceCents' own per-unit meaning) /
// per line for Service (mirrors Service.priceCents' own per-line meaning
// for FIXED pricing). Meaningful only when marginMode = NET_AMOUNT.
marginAmountCents           Int?
// 10000 = 100%, same basis-point convention as
// Company.vatRateBasisPoints/Service.percentageBasisPoints. Computed
// against the item's own HT price. Meaningful only when
// marginMode = PERCENTAGE.
marginPercentageBasisPoints Int?
```

All three stay `null` on every existing row after migration — no backfill,
no behavior change until an artisan opts in, same "boots identically"
posture every optional-field phase in this app follows.

## Correction vs. the original plan (found while implementing)

The original draft below assumed `marginMode` would carry
`@IsOptional() @IsEnum(MarginMode) @ProductMarginConsistency()` together,
mirroring `ServicePricingMode`'s own decorator stack. **That's a real bug,
caught by this phase's own DTO tests before it shipped**:
`class-validator`'s `@IsOptional()` skips *every* validator on the property
it decorates — including custom ones — the moment that property is
`null`/`undefined`. Since `marginMode` unset is exactly the case the
consistency check most needs to police ("nothing else may be set either"),
pairing `@IsOptional()` with the custom validator on the same property
silently disabled the one rule that mattered most, confirmed by a failing
test (`rejects marginAmountCents set with no marginMode`) that passed with
zero validation errors before the fix. Fixed by dropping
`@IsOptional()`/`@IsEnum()` from `marginMode` entirely: `ProductMarginConsistency`/
`ServiceMarginConsistency` now do their own enum-membership check and
handle `null` themselves, so the validator always runs. See both
validators' own comments for the full explanation.

## Checklist

### Backend — schema & migration

- [x] `MarginMode` enum added to `schema.prisma`.
- [x] Three columns added to `Product` and to `Service`, with a comment on
      each pointing back to this doc (same convention as every other field
      in this file).
- [x] Migration generated (`prisma migrate dev`) — purely additive,
      nullable columns, no data migration needed.

### Backend — validation

- [x] New `MarginConsistencyValidator` (custom `class-validator`
      constraint), same file shape as
      `backend/src/service-catalog/dto/service-pricing-consistency.validator.ts`
      and `backend/src/discount/dto/discount-consistency.validator.ts`.
      Rules:
  - `marginMode` unset (`null`/`undefined`) ⇒ both
    `marginAmountCents`/`marginPercentageBasisPoints` must be unset.
  - `marginMode = PERCENTAGE` ⇒ `marginPercentageBasisPoints` required,
    `1`–`10000` inclusive (0% isn't "no margin," it's "no margin
    configured" — represented by `marginMode = null` instead, so 0 is
    rejected rather than accepted as a confusing synonym);
    `marginAmountCents` must be unset.
  - `marginMode = NET_AMOUNT` ⇒ `marginAmountCents` required, `> 0`;
    `marginPercentageBasisPoints` must be unset. **When the DTO's own
    `priceCents` is present** (always true for `Product`; true for a
    `Service` only when `pricingMode = FIXED`), also reject
    `marginAmountCents > priceCents` — a per-unit margin can't exceed the
    per-unit price it's carved out of. Skipped for a `PERCENTAGE`-priced
    service (no fixed `priceCents` to bound against at save time — that
    service's actual amount is only known per-invoice).
  - **Two thin validators, not one shared one** (`ProductMarginConsistency`/
    `ServiceMarginConsistency`) — Product's `priceCents` is always present,
    Service's is only present for `pricingMode = FIXED`, and forcing one
    generic validator to branch on that difference read more awkwardly than
    two small entity-scoped ones, matching this codebase's existing
    one-validator-per-entity precedent.
- [x] `CreateProductDto`/`UpdateProductDto`/`CreateServiceDto`/
      `UpdateServiceDto`: three new optional fields. No `@ApiProperty`/Swagger
      decorators added — this codebase's existing `activityCategory` field
      on both DTOs has none either (checked before assuming otherwise), so
      there was nothing to mirror.
- [x] `ProductRepository`/`ServiceCatalogRepository` create+update: persist
      the three fields; on update, explicitly null out whichever of
      `marginAmountCents`/`marginPercentageBasisPoints` the new
      `marginMode` doesn't use — same "explicitly nulled to whichever the
      new mode doesn't use" pattern already commented on
      `ServiceCatalogRepository.update` for `pricingMode`.
- [x] `ProductProfile`/`ServiceProfile` (the entity type aliases over the
      generated Prisma model) already expose every column on the model with
      no allow-list to update — the three new fields reach the API response
      for free, confirmed rather than assumed.

### Frontend — catalog forms

- [x] `frontend/src/app/core/models/margin.model.ts`: new shared
      `MarginMode` union type (not duplicated per-entity like
      `ServicePricingMode` — this one is used by both `ProductProfile` and
      `ServiceProfile`, so a single shared file avoids an awkward
      cross-import between the two model files). Both models updated.
- [x] `product-form.page.html` / `service-form.page.html`: new "Marge"
      block inside the existing `<app-advanced-settings>`. Three-way toggle
      (Non renseignée / Montant net / Pourcentage), reusing the existing
      toggle's visual language extended by one option — NET_AMOUNT gets a
      euro input with the user's own "3€ sur les 6€" framing in the hint;
      PERCENTAGE gets an `<input type="range">` slider (Angular's built-in
      `RangeValueAccessor` handles it like any other reactive-forms
      control, no custom value parsing needed) with a live `{{ value }}%`
      readout, capped 1–100. Hint text makes clear this is internal-only,
      never shown to the client.
- [x] Both forms' submit mapping: build the DTO payload from whichever mode
      is selected, mirroring `service-form.page.ts`'s existing
      `setPricingMode`/`isPercentageMode` pattern (`setMarginMode`/
      `isMarginNetAmountMode`/`isMarginPercentageMode`).
  - `product-form.page.ts`'s form group gates submission on a blanket
    `this.form.invalid` (unlike `service-form.page.ts`, which already
    special-cased its own pricing controls out of that check) — giving
    `marginAmountEuros`/`marginPercentage` a `Validators.min` declared
    directly on the control would have poisoned that blanket check
    whenever margin is left unconfigured (default `0` failing `min(0.01)`).
    Fixed by leaving those two controls validator-free and checking them
    manually in `submit()` instead, only when `marginMode` actually
    requires one of them.

## Non-goals

- **No margin field on `Discount`** — see the track README.
- **No retroactive backfill or suggestion** ("this product's price
  suggests a X% margin based on your other items") — a plain empty field,
  same as every other optional catalog field on first ship.
