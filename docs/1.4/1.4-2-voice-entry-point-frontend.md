# Phase 1.4-2 — Frontend: Voice/Chat Entry Point on Invoice Creation

[← back to Phase 1.4 index](./README.md)

**Revision, 2026-08-29**: the review screen described below (highlighted
fields with an inline suggestion/prompt, corrected by direct editing) is
the actual design, specified by the user, replacing this doc's earlier
"clarifying question via chat" loop. See 1.4-1's own revision note — the
backend contract changed to match.

**Revision, 2026-08-29 (implementation)**: built and live-verified end to
end. Two deliberate deviations from the design below, decided during
implementation, plus two real bugs caught only by actually running it in a
browser — see this doc's own Live verification section for what was
tried and what came back:

- **The review screen's product/service lines are purpose-built rows, not
  `InvoiceLineFormComponent`/`InvoiceServiceLineFormComponent`.** Those are
  `FormGroup`-bound view components deeply coupled to `lines-step`'s own
  catalog-flyout/gallery-card machinery (folder grouping, collapse state,
  the quantity wheel picker) — built for picking from a live catalog, not
  for lightly correcting an already-resolved draft. Reusing them would
  have meant reimplementing a large slice of `lines-step`'s own FormArray
  setup for no real benefit. The review screen instead renders its own
  small editable rows, funneling into the exact same
  `InvoiceDraftStore.setLines()`/`setServiceLines()` — same data, same
  totals, same validation on submit. `app-invoice-deposit-field` (a
  genuinely self-contained controlled component) *is* reused as-is,
  unchanged.
- **No separate "Continuer en mode manuel" escape hatch was built** — the
  original design's flagged open question (would GUIDED lines convert
  cleanly to mode manuel's free-form table?) turned out to have a better
  answer once the review screen was routed as a `rapide` *child* (see
  below): the artisan already has full, lossless access to mode rapide's
  own "1. Client" and "2. Lignes & prestations" tabs from the review
  screen, reading and writing the *same* `InvoiceDraftStore` — no
  conversion needed, nothing to lose switching between them. A genuine
  mode-manuel escape hatch would need a real GUIDED→MANUAL conversion
  across two unrelated stores for strictly less capability than tab
  navigation already gives for free, so it was dropped rather than built
  for its own sake.

## Objective

### Engineering objective (verifiable)

A third mode on invoice creation, alongside mode rapide and mode manuel:
describe the devis/facture out loud (or typed), then land on a review
screen that looks like mode rapide's product/prestation/remise section
with the client shown at the top the way mode manuel shows it — doubtful
fields highlighted with an inline correction prompt — before continuing
into the same preview/aperçu step and the same success page every other
mode already ends on. This phase is the input surface, the review screen,
and the wiring into `InvoiceDraftStore` — no changes to the preview step or
success page themselves. Done, from an engineering standpoint, when: the
mode-choice option, capture (Web Speech API + text fallback), the review
screen (client block + line rows + the new needs-review highlight), and
the shared-store escape hatch (see revision note above) are all covered by
a green build/test run; `tsc`/`ng build` is clean; and the existing mode
rapide/mode manuel options show no regression. A developer should be able
to point at these checks and know the wiring is correct without having
personally spoken to the app. **Met**: `ng build` clean, 163/163 frontend
tests green (8 new), zero regressions in the existing suite.

## Voice review screen — design

The screen shown after a `resolved` response, before the existing preview
step. Not a new document pipeline or a new totals engine — a new
arrangement of components that already exist, pre-filled and annotated.

- **Routed as a `rapide` child** (`app.routes.ts`'s `rapide/revue`), inside
  the existing `InvoiceCreateShellPage` — `InvoiceTotalsSummaryComponent`
  (the live totals bar, bound to `draftStore.totalsPreview()`) is already
  mounted at that shell level and needed no new wiring to appear here too.
  This is what satisfies "toujours l'aperçu et le calcul automatique" —
  it's the same always-on calculation every step already has. Live-tested:
  a 25m² × 45€ line correctly totalled 1 125,00 € with no extra wiring.
- **Client block at the top**, styled like mode manuel's "Facturé à"
  section (`manual/invoice-create-manual.page.html`) — borderless,
  click-to-edit `customerName`/`customerAddress`/`customerEmail`/
  `customerPhone` fields that read as part of the document rather than a
  form. Pre-filled from the resolved customer when matched (`customerId`
  set, same "autofill, not a lock" rule as every other prefill in this
  app — still freely editable), left blank when `no_match`. Wired to
  `InvoiceDraftStore.setCustomer` instead of `ManualInvoiceDraftStore`
  (see 1.4-2's own `updateCustomer`/`applyCustomerSuggestion`).
- **Lines below** — see this doc's own revision note: purpose-built rows
  (description/quantity/unit/price, or name/amount for a service line),
  not `InvoiceLineFormComponent`/`InvoiceServiceLineFormComponent`. Same
  `InvoiceDraftStore.setLines()`/`setServiceLines()` either way.
- **"Needs review" highlight**, deliberately distinct from Angular's
  existing `ng-invalid.ng-touched` red-border convention
  (`frontend/src/styles.css`) — implemented as plain conditional Tailwind
  classes (`border-warning`/`bg-warning-subtle`, both pre-existing
  semantic tokens, no new CSS needed) rather than a new directive, plus a
  small shared `NeedsReviewHintComponent`
  (`voice/needs-review-hint.component.ts`) rendering the caption:
  - `suggestion` present → *"Vous vouliez dire « {suggestion.label} » ?"*
    — clickable, one-tap-applies the suggestion (looked up against the
    already-cached full catalog record — `InvoiceDraftStore.customers()`/
    `products()`/`services()` — so address/email/phone/unit/price all
    come along, not just the label).
  - No `suggestion` → *"Vérifiez ce champ s'il vous plaît."* Live-tested:
    an unmatched product line rendered exactly this caption in amber,
    visually distinct from a real (red) validation error.
  - `document_type_conflict` — originally scoped to "highlights the
    deposit section" only; **live-testing found this invisible whenever
    the resolved document was a DEVIS**, since the deposit field itself is
    conditionally hidden for a DEVIS (matches the backend's FACTURE-only
    rule) — the conflict flag had nowhere to render. Fixed: the hint now
    renders in its own bordered banner in the DEVIS branch specifically,
    so the conflict is visible regardless of which side of the toggle is
    currently selected. See Live verification below.
  - The highlight clears the moment the artisan edits the field
    themselves (every `update*` method in
    `InvoiceCreateVoiceReviewStepPage` pairs the store write with the
    matching `VoiceDraftReviewStore.clear*` call), independent of whether
    they used the suggestion.
- **`notices`** (a dictated remise/TVA/etc. with no corresponding tool)
  render as a small dismissible banner above the rest of the screen — live
  -tested: a dictated "avec une remise de 10%" correctly surfaced the
  banner and correctly did **not** create any discount line, dismiss
  button confirmed working.
- From here, continuing goes straight into the existing preview/aperçu
  step exactly as mode rapide's own flow does (same shell, same store,
  same route), and the success page after creation is completely
  unchanged — this phase touches neither.

## Features

- [x] New option on `invoice-create-mode-choice.page` — "Décrire à voix
      haute" (grid widened to 3 columns). Deliberately no `[queryParams]`
      `type` on this card's link, unlike the other two — the artisan's own
      words decide the document type here, a pre-picked toggle value would
      only ever be stale or conflicting.
- [x] Capture (`voice/invoice-create-voice-capture.page.ts`): Web Speech
      API (`webkitSpeechRecognition`/`SpeechRecognition`, French,
      continuous+interim results) where supported
      (`speech-recognition-support.util.ts`, same "test the capability
      once, branch the template" convention as the PDF viewer fallback),
      with an always-present, always-editable textarea as both the
      live-transcript display and the typed-input fallback.
- [x] Submits to `POST /api/invoices/voice-draft`
      (`VoiceInvoiceDraftService`), 20s timeout matching
      `InvoiceService`'s own PDF-fetch convention.
- [x] Review-step page (`voice/invoice-create-voice-review-step.page.ts`,
      routed as `rapide/revue`) implementing the design above; on resolve,
      the capture page calls `InvoiceDraftStore.loadFromVoiceDraft(draft)`
      (new store method, mirrors `loadFromInvoice`'s "overwrite wholesale"
      pattern) and `VoiceDraftReviewStore.activate(draft)` (a second,
      narrower singleton holding just the `needsReview`/`notices`
      annotations — `InvoiceCustomerDraft`/`InvoiceLineDraft` have no such
      field and no other screen needs one) before navigating.
- [x] Needs-review highlight — `NeedsReviewHintComponent` +
      conditional `border-warning`/`bg-warning-subtle` classes, see design
      section above.
- [x] On `rejected`, a plain message on the capture page itself with a
      retry (edit the transcript, resubmit) — never opens the review
      screen with an all-blank flagged form.
- [x] Graceful handling of 1.4-1's rate/cost-limit response (429/503) via
      the same `friendlyErrorMessage(error: unknown)` pattern already used
      by `SourcingPanelComponent` — not yet actually triggerable in
      practice, since the bound engine (`RuleBasedDraftResolverService`,
      see 1.4-1) has no cap to hit; wired defensively for whenever the LLM
      engine is re-enabled.
- [x] Escape hatch — see this doc's own revision note: shared-store tab
      navigation instead of a dedicated mode-manuel button.
- [ ] ~~Playwright test~~ — **no Playwright (or any e2e) convention exists
      anywhere in this repo** (confirmed by search before starting: no
      `e2e/` directory, no config, not a dependency anywhere) — introducing
      the framework from scratch was out of scope for this phase. Live
      verification was instead done with a one-off `playwright-core`
      script driving the system's installed Chrome, kept in the session's
      scratchpad only (not committed) — see Live verification below for
      what it actually found. If this app adopts Playwright for real
      later, that script is a reasonable starting point for a first
      `invoice-create-voice.e2e-spec.ts`.

## Non-goals

- No persistent chat/history UI — corrections happen by directly editing
  the review screen's fields, not by a conversational back-and-forth.
- No offline recognition — relies on the browser's (online) speech
  recognition, or whatever the open question below resolves to.

## Open question (carried from the track README, not yet decided)

Web Speech API is free and requires no backend change, but has patchy
French accuracy and no Safari support — the text-field fallback above
covers that gap, but at the cost of a materially worse experience on
Safari specifically. Worth revisiting once there's a sense of how much of
the artisan base is on Safari/iOS before deciding whether a paid STT (e.g.
Whisper) is worth adding later — 1.4-1's endpoint is agnostic to this, so
it's a frontend-only decision that can change without touching the backend
phase at all. **Still open** — this pass didn't touch it; the mic path
itself wasn't exercisable in headless Chrome (no real microphone/speech
backend in that environment) — only the text fallback was actually driven
live, which is also exactly what a real Safari visitor gets.

## Live verification (2026-08-29)

Real dev stack (`docker compose`), a real registered test account, a real
`Customer`/`Product` created through the normal authenticated API — no
mocks — driven with a one-off `playwright-core` script against the
system's installed Chrome (headless), screenshots saved to the session
scratchpad. No `chromium-cli`/Playwright convention exists in this repo
(confirmed before starting), so this tooling was assembled fresh and not
committed.

**Mode-choice page**: all three cards render, correct copy including the
new "Décrire à voix haute" card
(`grid-cols-3`) — confirmed via `innerText` extraction, not just a visual
glance.

**Clean case** — dictated (typed, via the fallback) *"facture pour Xavier
Dupont, 25m2 de parquet chêne massif, acompte de 30%"* against a company
with exactly that customer and product saved: landed on `/rapide/revue`
with **zero** amber-highlighted fields — correct `FACTURE` selected,
"Xavier Dupont" in Facturé à, one product line ("parquet chêne massif",
25, m², 45 €), acompte auto-filled 30 % / 337,50 €, Sous-total HT and
Total TTC both correctly 1 125,00 €. Full screenshot confirms layout is
clean and correctly spaced.

**Flagged case** — *"facture pour Xavier Dupont, 10 mètres de lambris
inexistant"* (no matching product): first attempt exposed two real bugs,
both fixed and re-verified live before moving on:

1. **The product line rendered with unit "m²" instead of the backend's
   actually-resolved `LINEAR_METER`.** Root cause: a plain `[value]`
   binding on a native `<select>` whose `<option>`s are generated by
   `@for` can lose the race against Angular actually inserting those
   options — a known timing gotcha, not something the unit tests (which
   never touch the DOM) could have caught. Fixed by moving to a per-option
   `[selected]="option.value === line.unit"` binding instead, which has no
   such race. Confirmed directly against the backend first (`curl`, saw
   `"unit":"LINEAR_METER"` in the real response) before concluding the
   bug was frontend-only, not a regression of 1.4-1's own "bare mètres"
   fix from the same day.
2. **A `document_type_conflict` deposit flag was invisible when the
   resolved document was a DEVIS** — see the design section above for the
   root cause and fix. Re-verified live afterward with a transcript that
   deliberately combines a DEVIS with a requested acompte: the warning
   banner *"Un acompte ne s'applique pas à un devis — vérifiez le type de
   document ou retirez l'acompte."* now renders correctly even with the
   real deposit field hidden.

After both fixes: the unpriced line correctly showed `unit: ml`, an amber
border, and *"Vérifiez ce champ s'il vous plaît."* underneath — visually
distinct (amber, not red) from the app's real `ng-invalid.ng-touched`
style (confirmed zero elements matching that selector were present).

**Multi-flag case** — *"devis pour Xavier Dupont, 5 kg de mystère
introuvable, acompte de 15%"*: two flags rendered simultaneously (the
unmatched line, and the DEVIS/acompte conflict banner) with no overwriting
or hiding of one by the other — the third possible flag (an ambiguous
customer) didn't fire in this run: a second, similarly-named test customer
("Xavier Dupond") was on hand, but the transcript's exact-name dictation
("Xavier Dupont") matched one of them precisely, so a confident silent
resolve is the *correct* outcome, not a miss — `ambiguous_match` needs a
transcript that doesn't exactly match either candidate, which wasn't
tried this pass (the reason logic itself has its own passing unit test in
`fuzzy-confidence.util.spec.ts`).

**Notices** — *"facture pour Xavier Dupont, 25m2 de parquet chêne massif,
avec une remise de 10%"*: the dismissible notice banner rendered with the
correct message, no discount line was fabricated, and the dismiss button
correctly removed the banner.

**Not exercised this pass**: the one-tap "apply suggestion" click path (no
`ambiguous_match`/`low_confidence_match` case was actually triggered
live, see above); clicking through from the review screen to the real
preview step and "Créer la facture"; the real Web Speech API mic path
(no microphone/speech backend in headless Chrome — the text fallback is
the same code path a real Safari/Firefox visitor uses, so this isn't a
gap specific to this test method, but it is a gap in what's been proven).

Test data (a throwaway account, customer, and product) was cleaned up
from the dev database after this session.
