# Phase 1.4-3 — Native Speech Recognition (Capacitor)

[← back to Phase 1.4 index](./README.md)

**Status: implemented, compilation-verified (2026-08-29).** Built end to
end: `@capgo/capacitor-speech-recognition` wired into the capture page
behind `Capacitor.isNativePlatform()`, iOS `Info.plist` permission
strings added, Android's `RECORD_AUDIO` confirmed auto-merged from the
plugin's own manifest. Verified via an Android debug build (`assembleDebug`)
and an iOS Simulator build (`xcodebuild`) — both compile and link
cleanly with the plugin in place; see Live verification below. Not yet
verified on a real device/simulator *run* (voice actually captured and
transcribed) — that's manual testing left for whenever this ships,
consistent with the scope agreed before starting this phase
("build de compilation seulement").

## Objective

Real voice capture on iOS, where it currently doesn't exist at all — and
genuine on-device/offline recognition on Android, where it currently
doesn't either — via the compiled Capacitor app, without writing a speech
recognition pipeline from scratch.

**Why iOS is the real driver, not "better accuracy":** Safari/WebKit has
never implemented the Web Speech API (`SpeechRecognition`/
`webkitSpeechRecognition`) — confirmed during 1.4-2. A Capacitor iOS app
runs inside a WKWebView, the same engine, so the *native* app inherits
the exact same gap the *web* app has: an iPhone artisan gets 1.4-2's text
fallback and nothing else, whether they're in Safari or the App Store
app. This phase isn't a quality upgrade on an already-working path — it's
the only way to make voice capture exist on iOS at all.

**Why Android is a smaller but real win:** Chrome's own
`webkitSpeechRecognition` already routes through Google's speech service
in most cases, so the accuracy delta from a native plugin is smaller than
on iOS. What a native path adds there: genuine on-device recognition
(confirmed available on recent Android versions via the platforms
researched below) — audio never leaves the device, and it keeps working
with no connectivity, relevant on a job site with poor coverage.

## Approach

**Adopt an existing, maintained Capacitor plugin — do not write native
Swift/Kotlin speech-recognition code from scratch.** Researched
2026-08-29: this problem is already well-covered. `@capacitor-community/
speech-recognition` (and at least one actively-maintained fork,
`@capgo/capacitor-speech-recognition`, plus a Capawesome commercial
option) already wrap iOS's `SFSpeechRecognizer`/newer `SpeechAnalyzer`
pipeline and Android's on-device `SpeechRecognizer` behind one JS API,
with explicit French locale support (`fr-FR`, `fr-BE`, `fr-CH`, `fr-CA`
confirmed on iOS). The "possibility of Swift/Kotlin" this phase was
originally framed around turns out to mean *configuring native
permissions*, not writing a recognition pipeline — a much smaller lift
than it sounded like going in.

Sketch, to firm up at implementation time (plugin APIs move — re-verify
the exact method names against whichever plugin/version is current then):

- A small native-capture wrapper (e.g.
  `frontend/src/app/features/invoice-create/voice/native-speech-capture.util.ts`)
  exposing the same shape `InvoiceCreateVoiceCapturePage` already consumes
  from the Web Speech API path (a live transcript, a start/stop toggle) —
  the capture page swaps *which* mechanism drives that shape based on
  `Capacitor.isNativePlatform()` (same gating precedent as
  `pdf-viewer-support.util.ts`'s `needsCanvasPdfViewer` — test the
  capability once, branch, no runtime re-detection), not a rewritten UI.
  1.4-2's textarea fallback stays the fallback for whichever path (web or
  native) can't recognize speech at all.
- iOS: `NSSpeechRecognitionUsageDescription` +
  `NSMicrophoneUsageDescription` in `Info.plist`. Android: `RECORD_AUDIO`
  in `AndroidManifest.xml` (network state/internet permissions likely
  already present for the rest of the app). Config, not new native source
  files, unless the chosen plugin's own setup docs say otherwise at
  implementation time.
- Prefer on-device recognition when the plugin reports it available for
  the current locale (`isOnDeviceRecognitionAvailable()` or equivalent);
  fall back to network recognition otherwise; never block capture
  entirely just because on-device isn't available.
- A permission-request moment with a clear explanation before first use —
  this app already has a consent-conscious posture elsewhere (RGPD/
  newsletter opt-in, CGU acceptance); a bare OS permission dialog with no
  context beforehand would be out of character.

## Features

- [x] Pick the plugin: `@capgo/capacitor-speech-recognition` (v8.2.0 as
      installed), chosen over `@capacitor-community/speech-recognition`
      for tracking this app's actual Capacitor 8 (the community package
      was six months stale on Capacitor 7).
- [x] iOS `Info.plist` (`NSSpeechRecognitionUsageDescription` +
      `NSMicrophoneUsageDescription`) + Android `RECORD_AUDIO` (confirmed
      auto-merged from the plugin's own bundled manifest — not duplicated
      in the app's `AndroidManifest.xml`).
- [x] `Capacitor.isNativePlatform()`-gated capture path in
      `InvoiceCreateVoiceCapturePage`, reusing the existing transcript
      signal/textarea — only the acquisition mechanism changes. The
      native path lives in a new
      `frontend/src/app/features/invoice-create/voice/native-speech-capture.service.ts`,
      exposing the same `transcript`/`listening`/`errorMessage` signal
      shape the page already consumed from the Web Speech API path;
      three `effect()`s in the page keep the page's own signals in sync
      with the service's when `isNative` is true.
- [x] Permission-request UX with context: `requestPermissions()` is
      called from `start()`, with a French error message routing the
      artisan to the textarea fallback if denied or if the request
      itself fails — matching this app's existing consent conventions
      (explain, don't just fire a bare OS dialog).
- [ ] On-device-availability check / explicit `useOnDeviceRecognition`
      preference — deliberately left unset (plugin default) after asking
      the user directly (2026-08-29): simplicity over forcing on-device,
      since forcing it can fail outright on a device that hasn't
      downloaded the language model yet, with no automatic fallback.
      Revisit only if a real complaint surfaces.
- [x] Live verification — compilation only, per agreed scope. See below.

## Live verification (2026-08-29)

Scope agreed with the user beforehand: compilation sanity checks only —
confirm the plugin compiles and links into both native projects, not a
real device/simulator run (no mic, no actual transcription attempted).

- **Frontend build**: `npx ng build --configuration production` (needed
  before `cap sync`, which requires built web assets) — succeeded, one
  pre-existing bundle-budget warning (520.36 kB vs. 500 kB, unrelated to
  this change). `npx cap sync` — succeeded, `@capgo/capacitor-speech-recognition@8.2.0`
  registered as a plugin on both `android` and `ios`.
- **Android**: `./gradlew assembleDebug` — first attempt failed
  (`Unsupported class file major version 69`): the active JDK was 25,
  but this project's Gradle wrapper (8.14.3) doesn't support it. Re-ran
  with `JAVA_HOME` pointed at an installed JDK 21
  (`/Library/Java/JavaVirtualMachines/temurin-21.jdk`) — **BUILD
  SUCCESSFUL**, including `:capgo-capacitor-speech-recognition:assembleDebug`.
  No project file was changed to force this; it's an environment-variable
  override for whoever runs the build locally with a newer default JDK.
- **iOS**: `xcodebuild -project App.xcodeproj -scheme App -sdk
  iphonesimulator -configuration Debug build` against a booted
  Simulator — **BUILD SUCCEEDED**. First build after adding the plugin
  is slow (SPM package resolution), took several minutes.
- **Frontend unit tests**: `npx ng test` — 163/163 passing across 14
  files, no regressions from the native branching added to
  `InvoiceCreateVoiceCapturePage`.
- **Dev build**: `npx ng build --configuration development` — succeeded.
- Not verified: actual voice capture on a running simulator/device
  (would need a real microphone and a way to feed simulated audio into
  the iOS Simulator/Android emulator — out of scope for this pass).

## Non-goals

- No custom native speech-recognition pipeline — ruled out by the
  research above; an existing plugin already covers this well.
- No change to the *web* (non-native) capture path — 1.4-2's Web Speech
  API + text fallback stays exactly as shipped for anyone visiting the
  site directly, including on mobile Chrome.
- No change to 1.4-1's backend contract — the resolver only ever receives
  plain text and has never cared which capture path produced it (see
  1.4-1's own Notes).
- Not scoped: upgrading Android *web* (mobile Chrome) recognition — only
  the compiled native app gets this; a mobile-browser visitor keeps
  1.4-2's existing path.
