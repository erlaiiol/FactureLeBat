  upgrade — `PlanGateService` already exists for exactly this kind of

The security-critical re-validation pass
(`InvoiceVoiceDraftService.validateDraft`) didn't change at all — it
already operated on the engine-agnostic `RawVoiceDraftInput` shape, so it
applies identically to whichever engine produced the draft.

## Objective

### Engineering objective (verifiable)

Given a French transcript describing a devis/facture, produce **one**
draft, always, shaped exactly like what `InvoiceDraftStore` already
accepts from mode rapide — `documentType`, customer fields, `lines[]`/
`serviceLines[]`, optional deposit. Every field is either resolved with
confidence, or resolved with a best-effort value (or left blank) *and*
flagged `needsReview` with a reason and, where one exists, a suggested
correction — never silently wrong, **regardless of which `DraftResolver`
produced it**. The one exception is a transcript with no invoice-related
content at all, which rejects outright rather than opening an all-blank
flagged form. No document is ever created directly by this phase; it only
ever produces a draft for the new review step (1.4-2) to render and the
artisan to confirm or correct. Done, from an engineering standpoint, when:
every resolver output passes `InvoiceVoiceDraftService`'s server-side
re-validation (ids re-checked against the requesting company, every price
traced back to what a search actually returned — never trusted from either
engine's own claims); each engine's own tests deterministically cover a
clean resolve and every `needsReview` reason it can produce (mocked
`LlmClient` for the LLM engine, no live API calls in CI; mocked
`Customer`/`Product`/`ServiceCatalogService` for the rule-based engine); the
regex extraction utility has its own pure-function tests independent of any
DB; and the backend suite / `tsc --noEmit` are green. A developer should be
able to hand this off on the strength of these checks alone, with no live
call to anything external needed to trust the code paths.

### User-experience objective (to be verified against real usage)

The checks above only prove the code does what it was coded to do — they
don't prove the *resolution itself* is any good against how artisans
actually talk. This objective now applies to the rule-based engine first
(it's the one that actually runs) — and unlike the LLM engine, it can be
verified for real, for free, with no API key: call the endpoint directly
(no UI yet — that's 1.4-2) against a batch of realistic, unscripted French
transcripts — hesitations, regional phrasing, the kind of sentence an
artisan would actually say, not a clean written example — and record the
actual results, not just "tested":

- How often a correct match resolves with no flag at all vs. gets flagged
  `needsReview` unnecessarily (false-positive caution — annoying, but the
  safe direction to err in). **Expect this to happen more often than an
  LLM would** — a regex parser reads far less flexibly than a model, and a
  higher `needsReview` rate is the intended trade-off for zero cost, not a
  bug to chase away. See this doc's own Live verification section for a
  real example of exactly this (a bare "mètres" gap, found and fixed the
  same day).
- How often a *wrong* value resolves with no flag at all (the dangerous
  failure mode — this feeds a legal document, so this must be zero across
  the sample set before shipping, not just rare). This is the one number
  that must stay at zero regardless of which engine is bound.
- How the acompte/devis conflict check behaves on phrasing that doesn't
  cleanly say either word.

Write down the transcripts actually tried and what came back for each —
the point is a record future work can check against, not a pass/fail
checkbox. Whoever re-enables the LLM engine later should repeat this same
exercise against it once a real `LLM_API_KEY` is available — see this
doc's Live verification section for what's actually been done so far on
each engine.

## Transversal / non-functional concerns

Not transcript content — these hold regardless of what any single transcript
says, and a passing transcript table doesn't prove any of them.

- **Cross-tenant isolation of the fuzzy search itself.** Seed two
  companies with a same/similar-named customer or product and verify,
  directly at the repository level, that company A's search/resolution
  never surfaces or uses company B's row. This is a security property that
  must hold independent of which engine is calling it — see the
  re-validation tests already listed above, which cover the *output*; this
  covers the *search* that feeds it. Live-verified, see below.
- **Rate/cost limiting.** Only meaningful for the LLM engine — the
  rule-based engine has no per-call cost, so `isAvailable()` is always
  `true` and there's no cap to enforce. `LlmDraftResolverService` still
  owns its own daily cap (`VOICE_DRAFT_DAILY_CAP`/`VoiceDraftRequest`) for
  whenever it's re-bound.

## Approach

Two `DraftResolver` implementations behind one interface
(`draft-resolver.interface.ts`) — `InvoiceVoiceDraftService` (the
orchestrator) only ever calls `DRAFT_RESOLVER.resolve(companyId,
transcript)` and re-validates whatever `RawVoiceDraftInput` comes back; it
has no idea which engine is bound.

**`RuleBasedDraftResolverService` (bound today, `rule-based/`)** — no
external dependency, no fine-tuning, no self-hosted model:

- `voice-draft-rule-based-parser.util.ts` — pure regex/heuristic functions
  extracting document type (`devis`/`facture` whole-word match), a deposit
  (`acompte de N%` / `acompte habituel` against
  `Company.defaultDepositPercentageBasisPoints`), a customer-name candidate
  (`pour <phrase>`), and quantity+unit+description line candidates (a
  curated French unit vocabulary — `m²`/`m2`, `m³`/`m3`, `ml`, `kg`,
  `litre`, `heure`, `jour`, `forfait`, `unité`, with a bare "mètre(s)"
  fallback to `LINEAR_METER`). Every function's own comment documents what
  it can't handle (spelled-out numbers, "à"-phrased customers, mid-sentence
  self-correction) — see the transcript table above for the concrete
  consequences.
- `fuzzy-confidence.util.ts` — `pickBestMatch`, the one piece of judgment
  an LLM would otherwise make itself: given a company's fuzzy-search
  results (now scored — see below), decide whether to trust the top
  candidate outright (score ≥ 0.5), flag it as a low-confidence guess (a
  single candidate below that), or flag the whole set as `ambiguous_match`
  (top two within 0.1 of each other).
- `rule-based-draft-resolver.service.ts` — wires the two together: extract,
  fuzzy-search each candidate against this company's own catalog
  (`Customer`/`Product`/`Service`, via the same `searchFuzzy` methods the
  LLM engine's tools call), decide product-line vs. service-line by
  whichever catalog scored higher, and build the same `RawVoiceDraftInput`
  shape the LLM engine produces.

**`CustomerRepository`/`ProductRepository`/`ServiceCatalogRepository.searchFuzzy`
now return the pg_trgm similarity score alongside each row**
(`FuzzyMatch<T>`, `backend/src/common/fuzzy-match.ts`) — added specifically
so `pickBestMatch` has something to threshold on; the LLM engine's search
tools pass the score through too (harmless extra context for the model).

**`LlmDraftResolverService` (dormant, `llm/`)** — unchanged from this doc's
previous revision: a tool-use loop against a generic `LlmClient` interface
(`llm-client.interface.ts`), given read-only search tools scoped to the
requesting company and a system prompt describing the invoice/devis
domain. Not given free rein to write anything — every field it proposes
must resolve through a tool call, so hallucinating a client or a price is
structurally the same failure mode as a bad database read. `resolve_draft`
is its own terminal tool call, carrying the same `needsReview: { reason,
suggestion? }` shape on every field as the rule-based engine's output —
`reason` is one of `no_match`, `ambiguous_match`, `low_confidence_match`,
or `document_type_conflict`; `notices[]` carries anything dictated with no
corresponding field at all (a remise, a VAT override). `AnthropicLlmClientService`
is the one implementation bound to `LlmClient` today, chosen the same way
`GroqClientService` was for sourcing — not a permanent commitment.

## Data model / infrastructure

- [x] Enable the `pg_trgm` Postgres extension (migration
      `20260829090221_add_pg_trgm_fuzzy_search_indexes`).
- [x] Trigram (GIN) index on `Customer.name`, `Product.name`/`code`,
      `Service.name`/`code` (same migration).
- [x] `CustomerRepository.searchFuzzy(companyId, query)` and the
      `Product`/`Service` equivalents, returning `FuzzyMatch<T>[]` (row +
      pg_trgm score) — similarity-ordered, company-scoped the same way
      every other repository query here already is. Additive: the existing
      plain-substring `findAll` methods are untouched, per the track's
      non-goal on upgrading them. Exposed one layer up via
      `CustomerService`/`ProductService`/`ServiceCatalogService.searchFuzzy`,
      plus a `findByIdOrNull` on `ProductService`/`ServiceCatalogService`
      (`CustomerService` already had one) for re-validation.
- [x] `VoiceDraftRequest` (daily-cap counter) is now scoped to the LLM
      engine specifically (`LlmDraftResolverService`, via
      `InvoiceVoiceDraftRepository`) — the rule-based engine has no cost to
      cap, so it never writes to this table.

No persisted or ephemeral conversation state needed — the original
multi-turn design's `conversationId`/TTL machinery never existed in the
shipped code.

## Features

- [x] `POST /invoices/voice-draft` — body: `{ transcript }`. Returns either
      `{ status: 'resolved', draft }` (draft fields individually carrying
      `needsReview` per the shape above, `notices[]` inside the draft) or
      `{ status: 'rejected', message }`. (`InvoiceVoiceDraftController`.)
- [x] `DraftResolver` interface + `DRAFT_RESOLVER` DI token
      (`draft-resolver.interface.ts`) — the engine boundary; bound to
      `RuleBasedDraftResolverService` in `invoice-voice-draft.module.ts`.
- [x] `RuleBasedDraftResolverService` + its parser/confidence utilities
      (`rule-based/`) — the active engine, no external dependency.
- [x] `LlmDraftResolverService` (`llm/`) — the tool-use loop, fully wired
      and tested but **not bound** to `DRAFT_RESOLVER`; system prompt
      encodes the devis/facture vocabulary and the FACTURE-only acompte
      rule so the conflict is flagged rather than silently resolved either
      way.
- [x] Server-side re-validation of whichever engine's output
      (`InvoiceVoiceDraftService.validateDraft`/`resolveCustomer`/
      `resolveLine`/`resolveServiceLine`) — every `customerId`/`productId`/
      `serviceId`, **including any `needsReview.suggestion` id**, re-checked
      to actually belong to the requesting company (never trusted from
      either engine's own claims); every price/unit on a matched line
      overwritten from what that lookup actually returned. A defensive
      server-side re-check also forces `document_type_conflict` on a DEVIS
      deposit and `no_match` on any line/service-line that ended up
      unmatched, even if the resolving engine forgot to flag either.
- [x] `entryMode` on the resulting draft is always `GUIDED` — voice/chat
      dictation produces structured lines, never a `MANUAL` canvas row.
- [x] Per-company daily cap + burst throttle — see Data model above;
      LLM-engine-only now, since it's the only cost-bearing path.
- [x] Tests (67 total across the feature): `invoice-voice-draft.service.spec.ts`
      (the shared re-validation pass, engine-agnostic — mocks a generic
      `DraftResolver`, never a specific engine);
      `rule-based/rule-based-draft-resolver.service.spec.ts` +
      `rule-based/voice-draft-rule-based-parser.util.spec.ts` +
      `rule-based/fuzzy-confidence.util.spec.ts` (the active engine, pure
      functions tested independently of the resolver that wires them
      together); `llm/llm-draft-resolver.service.spec.ts` +
      `llm/voice-draft-response.util.spec.ts` (the dormant engine's own
      tool-loop mechanics, kept green so it's still trustworthy whenever
      it's rebound). **Not an automated repository-level test** for
      `searchFuzzy` — this codebase has none anywhere (see 1.3-4's own
      note on the same trade-off); verified instead directly against
      Postgres, see Live verification below.

## Non-goals

- No write to `Invoice`/`InvoiceLine` from this endpoint — creation still
  only happens through the existing invoice-creation path once the artisan
  confirms on the preview step, same as every other entry point.
- No multi-turn chat exchange with either engine — a doubtful field is
  corrected by the artisan directly editing it in the review screen
  (1.4-2), not by describing the correction verbally a second time.
- No multi-item batch parsing across several unrelated documents in one
  transcript — one devis/facture per call.
- No fuzzy search exposed on the existing `GET /customers`/`/products`/
  `/services` endpoints — see the track's scope decision.
- No runtime auto-selection between the two engines (e.g. "try rule-based,
  fall back to LLM on failure") — explicitly decided against for now: the
  rule-based engine alone is the whole story until there's a reason to
  reconsider (see this doc's third revision note).

## Live verification (2026-08-29)

**Full backend suite green (559 tests, 67 in this feature), `tsc --noEmit`
and `eslint` clean.**

**Real end-to-end run against the running dev stack — no mocks, no API
key needed** (this is the first time this phase could be verified this
way, precisely because the bound engine has no external dependency):
registered a real test account through `POST /auth/register`, created a
real `Customer` ("Xavier Dupont") and `Product` ("Parquet chêne massif",
4500cts/m²) through the normal authenticated API, then called `POST
/invoices/voice-draft` with this doc's own running example transcript
verbatim:

> "fais moi une facture pour Xavier Dupont je mets 25m2 de parquet chêne
> massif et je lui demande un acompte de 30%"

Result — every field resolved correctly with **zero** `needsReview` flags:
`documentType: FACTURE`, the real `customerId`, the real `productId` with
its real catalog price (4500, not a guessed number), `quantity: 25`,
`depositPercentageBasisPoints: 3000`. This is transcript #1 from the table
above, genuinely exercised end to end.

Also live-tested against the same running server:

- **Transcript #3** ("10 mètres de lambris exotique édition limitée", no
  matching product) — first attempt returned **zero lines at all**,
  silently dropping the item instead of flagging it: a real bug, caught
  only by trying it live. Root cause: the unit vocabulary recognized
  "mètres carrés"/"mètres cubes"/"mètres linéaires" but not a bare
  "mètres" on its own, so the whole quantity+unit match failed and nothing
  downstream ever saw a candidate to flag. Fixed by adding a bare
  "mètre(s)" fallback to `LINEAR_METER` (tried only after the more
  specific "carrés"/"cubes" patterns have had their chance — see the
  parser's own comment), re-verified live afterward: now correctly returns
  one line, `unit: LINEAR_METER`, `unitPriceCents: 0`,
  `needsReview: { reason: 'no_match' }`. Two new unit tests added for the
  fallback (and that it doesn't hijack the "carrés"/"cubes" cases).
- **Transcript #5** ("un devis... acompte de 20%") — live-confirmed
  `depositNeedsReview: { reason: 'document_type_conflict' }`, deposit
  value still carried through (20%) rather than silently dropped.
- **Transcript #10** ("quel temps fait-il aujourd'hui") — live-confirmed
  `status: 'rejected'` with the plain French message, no draft, no crash.
- **Transcript #14** ("l'acompte habituel", no percentage said) — not
  separately re-verified live in this pass (already covered by the
  resolver's own unit test against a mocked company default), but the same
  code path as the deposit checks above.
- **Cross-tenant isolation** — verified directly against Postgres (two
  temporary companies, same-named customer in each): a fuzzy search scoped
  to company A never surfaced company B's row. Same evidence this doc
  already recorded before the rule-based engine existed — the property
  lives in the repository layer, unaffected by which engine calls it.

**Not done**: the LLM engine (`LlmDraftResolverService`) has no equivalent
live run — no `LLM_API_KEY` was available, and it isn't the bound engine
right now anyway. Its own tool-loop mechanics are covered by
`llm/llm-draft-resolver.service.spec.ts` against mocked responses; the
*quality* of its resolution against real phrasing remains unverified,
same as this doc's previous revision noted, now simply lower-priority
since it's dormant.

## Notes

- Depends on Phase 15 (mode rapide's preview step / `InvoiceDraftStore`
  shape) and Phase 1.1-3 (Acompte, for the FACTURE-only rule this phase's
  conflict check enforces).
- **Engine choice, decided with the user, 2026-08-29**: an invoicing app
  shouldn't require an LLM subscription just to exist. The rule-based
  engine is free and requires no configuration at all — it's what every
  deployment of this app runs today, with zero setup and zero per-call
  cost. The LLM engine stays fully built and tested specifically so
  re-enabling it later (a fallback for what the rule-based engine can't
  resolve, or a Premium-tier upgrade via the existing `PlanGateService`)
  is a scoping/business decision when it comes up, not another
  implementation project.
- Whichever STT produces the `transcript` (see 1.4-2's open question) is
  irrelevant to either engine — both only ever receive plain text.
