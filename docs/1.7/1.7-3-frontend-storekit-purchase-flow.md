# Phase 1.7-3 — Frontend: Native StoreKit2 Purchase Flow, Restore, Conditional UI

## Objective

Replace Phase 22's iOS "link out to Safari to subscribe" pattern with a
real in-app purchase flow, gated to iOS only — web and Android keep the
existing Stripe Checkout redirect (`subscribe.page.ts`) completely
unchanged.

## Architecture

- **New plugin dependency**: whichever the Open Decision in the
  [track README](./README.md) resolves to — a RevenueCat-backed
  Capacitor plugin (e.g. `@capgo/capacitor-purchases`) or a thin
  StoreKit2-native Capacitor plugin if building it directly. Either way,
  it must resolve via **Swift Package Manager** — this project's
  `ios/App/` has no `Podfile` (confirmed: SPM via `CapApp-SPM/`, same as
  every other plugin here per Phase 22's own notes on `@capacitor/browser`'s
  SPM-only integration). Check the plugin's own install docs for SPM
  support before picking one; a CocoaPods-only plugin would be the first
  of its kind in this repo and adds a build-pipeline dependency the
  project has specifically avoided so far.
- **`IosPurchaseService`** (`core/services/ios-purchase.service.ts`),
  mirroring `AppleNativeLoginService`'s shape (Phase 1.5) — a thin
  wrapper around the plugin: `purchase(tier: PlanTier)`,
  `restorePurchases()`, `getActiveEntitlement()`. Same "one dedicated
  service per native capability" convention `AppleNativeLoginService`/
  `GoogleNativeLoginService` already established, not folded into
  `PlatformService` (which stays a pure capability-detection helper).

## Features

- [x] `IosPurchaseService.purchase(productId)`: triggers the plugin's
  purchase flow (this is what shows Apple's system purchase sheet — a
  real modal Apple renders, not anything this app draws), and returns the
  resulting transaction JWS for the caller to post to
  `POST /billing/apple/verify-purchase` (1.7-2). **Deviation from the
  sketch above, for the better**: takes a `productId` directly rather
  than a `PlanTier` mapped via a hardcoded frontend constant — the
  product id now comes from `GET /billing/plans`' new `appleProductId`
  field (1.7-2), so the frontend never hardcodes an Apple product id at
  all, matching this codebase's own "backend is the single source of
  truth for pricing" rule more strictly than originally planned.
  `subscribe.page.ts`'s `purchaseNative` caller then calls
  `billingService.refreshStatus()` on success, same refresh call
  `subscribe()`'s Stripe path already triggers.
- [x] `subscribe.page.ts`: the pricing-card grid (previously hidden
  entirely on iOS) now renders on iOS too, with each card's button
  calling `purchaseNative(plan.tier, plan.appleProductId)` instead of
  `subscribe(plan.tier)` when `platformService.isIosApp()`; falls back to
  "Bientôt disponible sur l'App Store" when `!s.appleConfigured ||
  !plan.appleProductId`, same shape the Stripe side already has for
  `!s.stripeConfigured || !plan.available`. The status section's old
  `openWebSubscriptionPage()` link-out button is replaced (see the next
  item) — this is the concrete change that supersedes Phase 22's
  decision; **still needs a cross-reference added to `docs/roadmap.md`'s
  Phase 22 section** (not done in this pass), matching how Phase 1.5 was
  cross-referenced back into Phase 22 when it shipped.
- [x] **"Restaurer mes achats" button** (Apple guideline 3.1.2 —
  mandatory on any app selling auto-renewable subscriptions): calls
  `iosPurchaseService.restorePurchases()`, re-verifies every returned
  entitlement against the backend in a loop, refreshes status. Lives in
  the status section on `/abonnement` directly (not buried in settings),
  alongside a "Gérer dans Réglages iOS" link
  (`PlatformService.openIosManageSubscriptionsSettings()`, a direct
  `itms-apps://apps.apple.com/account/subscriptions` navigation — an
  Apple subscription has no Stripe-portal equivalent, it's managed
  entirely through iOS Settings).
- [x] `PaywallModalComponent`'s iOS branch **removed entirely** rather
  than updated to call `purchaseNative` directly — its existing
  `goToSubscribe()` already just routes to `/abonnement`, which now
  handles the platform split internally, so the modal itself no longer
  needs any iOS-specific code at all. `TrialOfferModalComponent`'s iOS
  branch was **deliberately left as the Phase 22 external link-out** —
  its specific discounted price is a Stripe coupon with no Apple IAP
  equivalent (see the non-goal below), so routing it into a StoreKit
  purchase would silently fail to honor the price shown on the card;
  the comment there was updated to explain why it's the one iOS branch
  that didn't change.
- [x] Promo-code redemption and referral sections: kept hidden on iOS
  (`!platformService.isIosApp()`, unchanged) per the recommendation
  above — applied as-is, not re-confirmed with the user separately.

## Non-goals

- **No App Store "offer codes" / promotional offers.** Apple has its own
  discount mechanism for subscriptions (separate from Stripe coupons,
  configured in App Store Connect, redeemed via a different StoreKit
  API) — not built here; Phase 30's referral/promo-code system stays
  Stripe/web-only, per the recommendation above.
- **No Android equivalent.** Play Store Billing is a separate API
  (`@capacitor-community/billing` or similar) with its own review
  requirements — out of scope, since Phase 22 already established
  Android keeps the external-link/Stripe pattern.

## Verification caveat — read before marking this phase done

**A StoreKit purchase sheet is a real, modal, Apple-drawn UI element that
requires actual human interaction (Face ID/Touch ID or a password
confirmation) — it cannot be driven by any automation available in this
environment.** Per the existing iOS-simulator setup here (`make demo` +
`frontend/scripts/run-ios.sh dev`, no `idb`/Appium, Accessibility access
blocked), the purchase flow can be *built and code-reviewed* from here,
but **the actual tap-to-purchase-sheet-to-confirmation round trip must be
verified by the account holder, in Xcode, on the Simulator (with a local
`.storekit` StoreKit Configuration file for products that don't exist in
App Store Connect yet) or a real device against sandbox.** Do not report
this phase as "done" on the strength of a successful build alone — same
"not yet exercised on a real device" honesty Phase 1.5 and Phase 22 both
already recorded for their own native-only pieces, expected to apply here
too, more strictly (Phase 1.5's flow could at least be triggered
end-to-end in principle from the Simulator; a purchase sheet's
confirmation step generally cannot without a real signed-in sandbox
Apple ID on the Simulator itself).

## What shipped (2026-09-23) — code written, NOT Xcode/device-verified

Per the Open Decision resolution in the [track README](./README.md): a
**local, hand-written Capacitor plugin**, not a third-party npm package —
consistent with the build-it-in-house call made for the backend. No
`Podfile`/CocoaPods step introduced, no new npm dependency at all.

- **`frontend/ios/App/App/Plugins/StoreKitPurchasePlugin.swift`** (new
  file, first hand-written native Capacitor plugin in this repo — every
  prior native integration used an npm plugin package): registers via the
  modern `CAPBridgedPlugin` protocol (pure Swift, no `.m`/`CAP_PLUGIN`
  macro file needed — Capacitor 4+ supports this directly, and this
  project is on Capacitor 8.x). Three JS-callable methods (`purchase`,
  `restorePurchases`, `getActiveEntitlements`), each returning only a raw
  transaction JWS *string* (`VerificationResult.jwsRepresentation`),
  never a parsed/trusted object — StoreKit2's own client-side
  verification is a fast-fail check, not a substitute for the backend's
  independent re-verification (1.7-2). A `Transaction.updates` listener
  task starts in `load()` and runs for the plugin's whole lifetime (not
  just around an explicit `purchase()` call) and forwards each new
  transaction to JS via a `transactionsUpdated` event — Apple's own
  guidance that a subscription can renew/resolve while the app isn't in
  the foreground of a purchase flow. iOS deployment target is already
  15.0 (confirmed in `App.xcodeproj/project.pbxproj`), StoreKit2's
  minimum — no deployment-target bump needed.
- **`frontend/src/app/core/services/ios-purchase.service.ts`** (new):
  `IosPurchaseService` wraps the plugin via `registerPlugin('StoreKitPurchase')`
  — `purchase(productId)`, `restorePurchases()`, `getActiveEntitlements()`,
  `onTransactionUpdated(callback)` (wrapped in `NgZone.run`, since
  Capacitor plugin listener callbacks fire outside Angular's zone).
  `IosPurchaseCancelledError`/`IosPurchasePendingError` mirror
  `AppleNativeLoginCancelledError`'s "cancellation isn't a real error"
  precedent (Phase 1.5), detected off the native call's `.code` field the
  same way.
- **`subscribe.page.ts`/`.html`**: `purchaseNative(tier, appleProductId)`
  and `restorePurchases()` methods; the pricing-card grid's outer gate
  changed from "Stripe not ACTIVE/PAST_DUE" to a platform-conditional
  check (Apple's own ACTIVE/PAST_DUE on iOS, Stripe's on web/Android); the
  per-card button branches on `platformService.isIosApp()` between
  `purchaseNative`/`subscribe`; the status section's old link-out button
  became a "Restaurer mes achats" + "Gérer dans Réglages iOS" pair.
- **`frontend/src/app/core/services/platform.service.ts`**: new
  `openIosManageSubscriptionsSettings()` (`itms-apps://` direct
  navigation — not `Browser.open`, which only handles http(s)).
- **`frontend/src/app/core/models/billing.model.ts`**: `PlanOption`
  gained `appleProductId`, `BillingStatus` gained `appleConfigured` +
  `appleSubscriptionStatus`, mirroring the backend entities 1.7-2 added.
- **Verified in this pass**: `ng build` (full AOT template compile, catches
  binding/type errors in `.html` files too) is clean. **Not verified**:
  the Swift file has never been compiled — this environment has no Mac/
  Xcode. It needs to be added to the "App" target in Xcode (a manual,
  one-time step — Capacitor doesn't auto-discover a new native file
  dropped into `ios/App/App/Plugins/`) before any of it can even build,
  let alone be exercised. See the verification caveat above, which
  applies in full and is not weakened by "the code compiles against
  Angular's build" — that only proves the *TypeScript* side is
  well-typed, not that the native side works at all.

## Notes

- Depends on 1.7-2 for `POST /billing/apple/verify-purchase` to exist,
  and on 1.7-1 for real product ids to purchase against (a `.storekit`
  Configuration file lets this be built and locally tested before either
  finishes, using placeholder product ids that match what 1.7-1
  eventually creates for real).
- `PlatformService.isIosApp()` (Phase 22/1.5) is the only gate needed —
  no new platform-detection logic required.
