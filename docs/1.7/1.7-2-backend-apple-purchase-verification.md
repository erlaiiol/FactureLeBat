# Phase 1.7-2 — Backend: Apple Purchase Verification & Server Notifications V2

## Objective

Give the backend a second, independent way to know a company has an
active paid tier — resolved from Apple's App Store Server API/
notifications instead of Stripe — without disturbing how Stripe
subscribers are resolved today.

## Decision needed before starting (see track README's Open Decision 1)

This phase's shape depends on whether the user confirms RevenueCat (or
similar) vs. Apple's own `@apple/app-store-server-library`:

- **If RevenueCat**: this phase shrinks to wiring RevenueCat's webhook
  (`POST /billing/apple/rc-webhook`, HMAC-signed, one event type
  `INITIAL_PURCHASE`/`RENEWAL`/`EXPIRATION`/`CANCELLATION` switch,
  RevenueCat's dashboard maps its own product-id → entitlement) and
  storing RevenueCat's `app_user_id` on `Company` instead of an Apple
  `originalTransactionId` directly. Skip straight to "Data model" and
  "Tier resolution" below with `rcAppUserId` substituted wherever
  `appleOriginalTransactionId` is written.
- **If build-it**: everything below applies as written.

The rest of this doc assumes the build-it path, since that's the one
with real architectural decisions to record; the buy path is a strict
subset of it.

## Architecture

- **New library**: `@apple/app-store-server-library` (Apple's official
  Node/TypeScript SDK) — decodes and cryptographically verifies the JWS
  (`signedTransactionInfo`, `signedRenewalInfo`, and notification
  payloads) against Apple's root certificates, and provides a client for
  the App Store Server API itself (transaction history lookups, sending
  a test notification). Same "one purpose-built library over bespoke
  crypto" reasoning `apple-signin-auth` was chosen for in Phase 1.5 — do
  not hand-roll JWS/x5c chain verification.
- **Auth to Apple's API**: a signed JWT (ES256, the `.p8` App Store
  Server API key from 1.7-1), same shape as `apple-signin-auth`'s
  `getClientSecret` already produces for Sign in with Apple, but a
  distinct key/Key ID/Issuer ID (`APPLE_IAP_KEY_ID`/`APPLE_IAP_ISSUER_ID`/
  `APPLE_IAP_PRIVATE_KEY`) — do not conflate with `APPLE_KEY_ID`/
  `APPLE_PRIVATE_KEY`.
- **New module surface, inside the existing `backend/src/billing/`
  folder** (not a separate top-level module — same one-`billing/`-folder
  convention Phase 30 already keeps for Stripe): `apple/` subfolder,
  mirroring the existing `stripe/` subfolder shape (`stripe-client.service.ts`
  → `apple/apple-server-client.service.ts`).

## Data Model

- `Company.appleOriginalTransactionId` (`String?`, unique) — Apple's
  durable per-subscription identity, the `originalTransactionId` field
  every transaction/renewal JWS carries. Directly analogous to
  `stripeSubscriptionId`; resolved and stored the first time a purchase
  is verified.
- `Company.appleSubscriptionPlanTier` (`PlanTier?`) — mirrors
  `subscriptionPlanTier`, resolved from the purchased product id via a
  new `APPLE_PRODUCT_ID_ESSENTIEL`/`_PRO`/`_PREMIUM` → `PlanTier` map in
  `plan-config.ts`, same shape as `StripeClientService.resolveTierFromPriceId`.
- No new table for notification history — log and act, same as
  `handleWebhook`'s Stripe switch today does nothing beyond
  `applySubscriptionEvent`. Add one only if debugging in production
  proves it's needed.

## Features

- [x] `POST /billing/apple/verify-purchase` (authenticated): frontend
  posts the signed transaction JWS immediately after a successful native
  purchase (StoreKit2's `Transaction.currentEntitlements` /
  `Transaction.updates` hand this back). Backend verifies the JWS via
  `app-store-server-library`, extracts `originalTransactionId` +
  `productId`, maps `productId` → `PlanTier`, and persists via a new
  `BillingRepository.applyAppleSubscriptionUpdate` — same "resolved from
  the signed payload, never trusted from an unsigned client field"
  posture `applySubscriptionEvent` already has for Stripe's price id.
- [x] `POST /billing/apple/notifications` (public — no raw-body handling
  needed here unlike Stripe's webhook: the proof of authenticity is the
  JWS string itself, not an HMAC over exact request bytes, so a normal
  parsed JSON body works). **Implemented as a switch on `data.status`**
  (Apple's `Status` enum: `ACTIVE`/`EXPIRED`/`BILLING_RETRY`/
  `BILLING_GRACE_PERIOD`/`REVOKED`) **rather than `notificationType`** as
  originally sketched here — more precise (`notificationType` has ~20
  variants across renewal/refund/offer/consent events, most of which
  don't change subscription status at all; `data.status` is exactly the
  field App Store Server Notifications documents as "the subscription's
  status as of this notification"). `TEST` pings and any notification
  with no `data.signedTransactionInfo`/`status` are ignored rather than
  erroring. Resolves the company by `appleOriginalTransactionId`, calls
  `applyAppleSubscriptionUpdate`.
- [ ] Register the notification URL with Apple (`AppleServerClientService.
  requestTestNotification` exists and is unit-callable, but nothing in
  1.7-2 calls it yet — no admin route was built for it; needs 1.7-1's
  real webhook URL/credentials to be worth exercising at all).
- [x] Extend `getEffectivePlanTier` (`plan-gate.service.ts`) to take the
  higher of **three** sources instead of two: Stripe subscription tier,
  Apple subscription tier, granted tier (`grantedPlanTier` +
  `premiumGrantedUntil`). Same `PLAN_TIER_ORDER`/`higherTier` comparator
  Phase 30 already built — this is purely adding a third argument to an
  existing max-of-N call, not new comparison logic.
- [x] `PlanTier` resolution failure mode: an Apple product id that
  doesn't match any configured `APPLE_PRODUCT_ID_*` env var logs a
  warning and resolves to `null` — same deliberately-safe-not-guessed
  failure mode `resolveTierFromPriceId` already has for Stripe.

## Non-goals

- **No refund-driven downgrade beyond what Apple's own notification
  already tells us.** `REFUND`/`REVOKE` notifications flip the company
  back off that tier; no separate reconciliation job polling Apple for
  drift — same trust-the-webhook posture the Stripe side already has.
- **No server-to-server subscription *creation* or price changes from
  this backend.** Apple's subscription/price management stays entirely
  in App Store Connect (1.7-1) — this phase only ever reads/verifies,
  never writes subscription state to Apple.

## Notes

- Depends on 1.7-1 for real product ids and the App Store Server API key
  — can be built and unit-tested against fixture JWS payloads before
  1.7-1 finishes, but can't be exercised against real Apple
  infrastructure until it does.
- `AuthService`'s Apple Sign-In `.p8` handling (Phase 1.5,
  `common/secret-crypto.util.ts`) is a separate credential from this
  phase's App Store Server API key — don't reuse the encryption-at-rest
  helper's existing `APPLE_PRIVATE_KEY` env var name for the new key,
  name it `APPLE_IAP_PRIVATE_KEY` to keep the two unambiguous in
  `.env`/`infra/.env`.

## What shipped (2026-09-23) — build-it-in-house path, code + tests, not yet live-verified

The Open Decision above resolved to Apple's own library — everything below
is the "build-it" path in full, not the RevenueCat shortcut.

- **Schema**: `Company.appleOriginalTransactionId` (unique, nullable),
  `Company.appleSubscriptionStatus` (`SubscriptionStatus`, default `NONE`,
  reuses the existing enum — no new one needed), `Company.
  appleSubscriptionPlanTier` (`PlanTier?`) — migration
  `20260923150000_add_apple_iap_subscription` (hand-written, same
  precedent as Phase 30's own hand-written migration; generated via
  `prisma migrate diff` against a throwaway local Postgres since this
  environment has no interactive TTY for `prisma migrate dev`, then
  verified with `prisma migrate deploy` + a drift check — zero drift).
- **`backend/src/billing/apple/apple-server-client.service.ts`**: mirrors
  `StripeClientService` exactly. Builds two `SignedDataVerifier` instances
  (Production + Sandbox) and two `AppStoreServerAPIClient` instances at
  construction; `verifyTransaction`/`verifyNotification` try Production
  first and fall back to Sandbox only on `VerificationStatus.
  INVALID_ENVIRONMENT` (Apple's own documented pattern — a live app's
  users can be TestFlight/sandbox testers or genuine purchasers at once).
  `resolveTierFromProductId`/`productIdForTier` mirror the Stripe price-id
  map both directions (the latter feeds `GET /billing/plans`, see below).
  Reuses Phase 1.5's `APPLE_CLIENT_ID` as the bundle id rather than a
  second env var for the same value. Apple's two DER root certificates
  (`AppleRootCA-G3.cer`, `AppleIncRootCertificate.cer`) are bundled in
  `apple/certs/` — public, non-secret files downloaded directly from
  `apple.com/certificateauthority`/`apple.com/appleca`, not fetched at
  runtime.
- **`backend/src/billing/apple/apple-subscription-status.util.ts`**:
  `mapAppleSubscriptionStatus` (Apple's 5-value `Status` enum → this
  app's 3-value `SubscriptionStatus`, same shape as
  `mapStripeSubscriptionStatus`) and `statusFromVerifiedTransaction` (used
  only right after a client purchase, before any Server Notification has
  arrived — ACTIVE unless the transaction is already revoked or past its
  `expiresDate`).
- **`BillingService.verifyApplePurchase`** (`POST /billing/apple/
  verify-purchase`, authenticated): the one place `appleOriginalTransactionId`
  gets linked to a company — companyId comes from `CurrentUser`, never
  the client payload. **`BillingService.handleAppleNotification`**
  (`POST /billing/apple/notifications`, public): App Store Server
  Notifications V2 handler, resolves the company by
  `appleOriginalTransactionId` (via the new `BillingRepository.
  findCompanyIdByAppleOriginalTransactionId`), ignores `TEST` pings and
  any notification with no `data.signedTransactionInfo`/`status`
  (one-time-charge/external-purchase-token events, not a subscription
  state change).
- **`PlanGateService.getEffectivePlanTier`** extended from a 2-source to a
  3-source `higherTier` chain (Stripe, Apple, grant) — `EffectiveTierFields`
  grew the two Apple fields; every existing 2-source test still passes
  unmodified, plus 5 new dedicated cases proving Apple slots in as a
  genuine equal (an Apple-only tier resolves, a non-ACTIVE Apple status is
  ignored even with a tier on file, either side can out-rank the other,
  and a grant still beats both).
- **`GET /billing/plans`/`GET /billing/status`** gained `appleProductId`
  per tier and `appleConfigured`/`appleSubscriptionStatus` respectively —
  same "backend is the only source of truth, frontend never hardcodes a
  product id" reasoning `available`/`stripeConfigured` already have for
  Stripe.
- **`AdminRepository`**'s `ADMIN_USER_ROW_SELECT` gained the two Apple
  columns — `AdminService.toSummary`'s `getEffectivePlanTier`/
  `hasPremiumAccess` calls would otherwise fail to type-check once
  `EffectiveTierFields` grew those fields, and an admin needs to see a
  company's real effective tier even when it comes from Apple, not Stripe.
- **Tests**: `apple-subscription-status.util.spec.ts` (new, 6 cases),
  `plan-gate.service.spec.ts` (+5 cases for the 3-way resolution),
  `billing.service.spec.ts` (+8 cases for `verifyApplePurchase`/
  `handleAppleNotification`, covering the link-on-first-verify flow, a
  revoked/stale transaction, an unresolvable product id, a missing
  `originalTransactionId`, `TEST` pings, `EXPIRED`→`CANCELED` mapping, and
  an unknown-`originalTransactionId` notification being a safe no-op).
  Full backend suite: 649 passing (6 pre-existing, unrelated failures in
  `facturx.service.spec.ts` — a `--experimental-vm-modules` environment
  gap that predates this phase). `tsc --noEmit` clean apart from 2
  pre-existing, unrelated fixture errors (`preferKeyboardQuantityInput`).
- **Not done, deliberately**: `AppleServerClientService.requestTestNotification`
  exists but nothing calls it yet — no admin route was built to trigger it
  (kept for 1.7-1's manual verification step and future ops use, per that
  phase's own "Hand-off to 1.7-2" note).
## Update (2026-09-28) — real credentials wired in, one real bug caught and fixed

1.7-1 is now done except the sandbox tester and the numeric App Store ID
(see that phase's own updated status). `APPLE_IAP_KEY_ID`/
`APPLE_IAP_ISSUER_ID`/`APPLE_IAP_PRIVATE_KEY`/`APPLE_PRODUCT_ID_ESSENTIEL`/
`_PRO`/`_PREMIUM` are live in both `backend/.env` and `infra/.env` with
the user's real App Store Connect values.

**A real bug was caught by actually running `AppleServerClientService`
against these real credentials, not just reading Apple's library docs**:
its own `SignedDataVerifier` constructor doc comment reads as if
`appAppleId` (→ `APPLE_APP_ID`) is optional ("omitted in the sandbox
environment"), but the **Production** verifier's constructor in fact
throws synchronously — `Error: appAppleId is required when the
environment is Production` — if it's missing. Since this service always
builds both the Production and Sandbox verifiers together (see
"Architecture" above — a live app's users can be either at once), this
would have crashed `AppleServerClientService`'s construction, and with it
the whole Nest app's bootstrap, the moment `APPLE_IAP_KEY_ID`/
`_ISSUER_ID`/`_PRIVATE_KEY` were set without `APPLE_APP_ID` alongside
them — exactly the state this deployment was in before this was caught.
**Fixed**: `APPLE_APP_ID` folded into the same all-or-nothing
`isConfigured()` gate as the other 4 values, so a deployment with it
still missing degrades to "Apple IAP disabled" (both routes 503) instead
of crashing on boot — same safe-unconfigured posture every other optional
credential in this app already has. `backend/.env.example`/
`infra/.env.example`'s comments were corrected to stop calling
`APPLE_APP_ID` optional.

Verified via a standalone script instantiating `AppleServerClientService`
directly against the real `.env` values (no Nest DI, no database needed)
— confirms `productIdForTier`/`resolveTierFromProductId` correctly
resolve the 3 real product ids from App Store Connect, and that
`isConfigured()` now correctly reports `false` (rather than crashing)
with `APPLE_APP_ID` still unset. Full billing suite (79 tests) still
green after the fix.

**Still blocking real end-to-end verification**: the numeric App Store
ID. Nothing else is missing on the backend side.

- **Genuinely unverified against Apple's live sandbox/production
  endpoints** (JWS verification against a *real* signed transaction,
  `requestTestNotification` actually reaching Apple, a real webhook
  delivery) — only unit-tested against hand-built fixture payloads and,
  as of this update, real-but-inert credentials. Needs `APPLE_APP_ID` at
  minimum, and a real purchase from 1.7-3's (still Xcode-unverified)
  native UI to test the full loop.
