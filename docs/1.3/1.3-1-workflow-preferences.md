# Phase 1.3-1 — Workflow Preferences: Settings Model & Customizable Controls

[← back to Phase 1.3 index](./README.md)

## Objective

The control surface for the whole track: lets an artisan pick, independently,
which parts of the pipeline should run automatically — without yet building
any of the automation behavior itself (that's 1.3-2 through 1.3-4). Ships
first so every later phase has a real preference to read instead of each
inventing its own.

## Data Model

- `Company.autoAttachFacturX Boolean @default(false)` — email a FACTURE and
  it's the Factur-X hybrid, not the plain PDF, no extra click ([1.3-2](./1.3-2-auto-facturx-email.md)).
- `Company.autoTransmitViaPa Boolean @default(false)` — only meaningful once
  SUPER PDP is connected; the toggle itself is disabled (not just unchecked)
  until then ([1.3-3](./1.3-3-delayed-auto-transmit.md)).
- `Company.autoSyncReceivedInvoices Boolean @default(false)` — background
  sync of the reception inbox instead of the manual "Actualiser" click
  ([1.3-4](./1.3-4-auto-reception-sync.md)).

Three independent booleans on purpose, not one "mode" enum — real
preferences don't collapse onto a single manual/automatic axis (wanting
Factur-X always attached to emails while still personally deciding when
something goes to the PA is a completely reasonable combination), and three
plain toggles is simpler to reason about and to extend later than a growing
list of named presets.

## Decided/discovered during implementation (2026-08-24)

- **Required, not optional, DTO fields** — see the Backend checklist's own
  deviation note above.
- **Server-side gate is a silent coercion, not a rejected request** — turning
  on `autoTransmitViaPa` while disconnected doesn't fail the whole `PATCH
  /company` call (which would also block every *other* legitimate field in
  the same request); it just saves `false` for those two fields and `true`
  for everything else genuinely changed. Under normal use the UI's own
  `.disable()` already prevents this path from being reached at all — this
  is a pure defense-in-depth backstop, not an expected user-facing error
  case, so a silent correction reads better than an error toast for
  something the artisan didn't knowingly attempt.
- **The disabled-checkbox mechanism was the one real design decision in this
  phase** — see the Frontend checklist's note above. Getting this wrong
  (template `[disabled]` alongside `formControlName`) would have been an
  easy, subtle bug (Angular's own dev-mode warning catches it, but it's the
  kind of thing that's easy to miss in a quick manual check).

## Non-goals

- No automation behavior in this phase — it only stores and exposes the
  preference. 1.3-2/1.3-3/1.3-4 are what actually read and act on it.
