# Phase 1.3-4 — Automatic Reception Sync

[← back to Phase 1.3 index](./README.md)

## Objective

With `autoSyncReceivedInvoices` on, the reception inbox (Phase 1.2-5) keeps
itself current without the artisan ever clicking "Actualiser" — relevant
given reception becomes mandatory 2026-09-01, a date the 2026-08-25 review
flagged as imminent and easy to miss.

## Checklist

### Backend

- [x] New `ReceivedInvoiceSyncCronService`
      (`received-invoice/received-invoice-sync-cron.service.ts`, mirroring
      `ReminderCronService`'s/1.3-3's `AutoTransmitCronService`'s shape):
      `@Cron(CronExpression.EVERY_DAY_AT_7AM, { timeZone: 'Europe/Paris' })`.
- [x] `CompanyRepository.findCompaniesForAutoSync()` — one cross-tenant
      query (`autoSyncReceivedInvoices: true, superPdpConnectedAt: { not:
      null }`), not an `isSuperPdpConnected` check per row (avoids N+1).
- [x] Calls `ReceivedInvoiceService.sync(companyId)` unchanged — no new
      sync logic.
- [x] Logs (`Logger.warn`), never throws, on a per-company failure.
- [x] Registered in `received-invoice.module.ts`. **Deviation from the
      plan**: also had to add `CompanyModule` to that module's own
      `imports` — `InvoiceModule` (already imported for
      `CompanySuperPdpService`) doesn't re-export `CompanyModule`, so
      `CompanyRepository` wasn't actually reachable from here without
      importing it directly. Caught by `tsc`/NestJS's own DI resolution,
      not by guessing at the module graph.

### Frontend

- [x] Confirmed, no changes made — the manual "Actualiser" button and
      `received-invoice-list.page.html` are untouched.

### Tests

- [x] Backend: new `received-invoice-sync-cron.service.spec.ts` — syncs
      every company the query returns, logs and continues past a
      per-company failure, no-ops when nothing is eligible.
- [x] **Not unit-tested** (consistent with 1.3-3's own precedent): whether
      `findCompaniesForAutoSync`'s Prisma query itself correctly excludes
      a disconnected company or a connected one with the toggle off — this
      codebase has no repository-level unit tests anywhere, and the cron
      service's own test can only ever assert on what the (mocked) query
      returns, not the query's own `WHERE` correctness. Verified instead
      directly against Postgres (see below).

**Live verification (2026-08-24)**: rebuilt the backend
(`docker compose ... up --build -d -V backend`) — booted cleanly with the
new cross-module `CompanyModule` import and the new `@Cron` job
registered, no circular-dependency or DI errors. Directly confirmed
`findCompaniesForAutoSync`'s exact `WHERE` clause against real Postgres
data: flipped a demo company's `autoSyncReceivedInvoices`/
`superPdpConnectedAt` on via `psql`, ran the equivalent `SELECT`, got
exactly that one company back; reverted immediately after. Did not wait
for a real 7am cron tick (impractical to wait out in-session) — the
sweep's own per-row behavior is covered by the unit tests above instead.

## Non-goals

- No push notification when a new received invoice lands in this phase — a
  natural next bucket for
  [1.3-5](./1.3-5-reminders-deadline-visibility.md)'s digest
  infrastructure, deliberately not bundled in here to keep this phase small
  and focused on the sync mechanism itself.

## Notes

- Depends on [1.3-1](./1.3-1-workflow-preferences.md) (the toggle) and
  Phase 1.2-5 (`ReceivedInvoiceService.sync`, called unchanged).
- Daily cadence, not more frequent — SUPER PDP's public spec still
  documents no webhook mechanism (confirmed during Phase 1.2-5), so this is
  polling either way; daily is proportionate to how often a supplier
  invoice actually needs to be *seen*, not a real-time inbox.
