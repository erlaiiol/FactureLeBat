# Phase 1.3-7 — Compliance Explainer: Obligations & What To Do in FactureLe

[← back to Phase 1.3 index](./README.md)

## Objective

Requested by the user (2026-08-25, same day as the rest of this track):
none of 1.2-6's deadline banner, 1.3-1's toggles, or 1.3-6's compliance
snapshot actually *explain* the reform — an artisan sees dates and status,
not what the obligations are, whether going through a third-party platform
is really mandatory, or how this relates to their separate URSSAF
declaration. This phase adds a compliance explainer answering exactly
those questions, placed in company settings (not Activity Analytics) since
that's where the actual controls (PA connection, automation toggles) live
— the explanation sits right next to the buttons it explains, not in a
separate tab the artisan has to cross-reference.

## Placement decision

Company settings' existing "Facturation électronique" section (Phase
1.2-6/1.3-1), not Activity Analytics (1.3-6) — the user left this open
("selon ce qui t'apparaît le plus pertinent"). Reasoning: 1.3-6 is a
status view (*is it working?*), this is an action-oriented explainer
(*what do I need to do, and where do I click?*) — it belongs next to the
deadline banners and the connect/automation controls it's explaining, not
next to a revenue chart. A single small "En savoir plus sur vos
obligations" disclosure, not a permanent wall of text — this app's own
restraint precedent (compare the settings page's existing
`app-field-hint` pattern: a one-line hint under a field, not a paragraph
always on screen).

## Content — verified against this project's own prior research, not re-derived from scratch

Five points, each answering one part of the user's own request:

1. **Réception obligatoire dès le 1ᵉʳ septembre 2026** (every VAT-liable
   business) — what to do: connect SUPER PDP in this same section, check
   "Factures reçues" (Phase 1.2-5).
2. **Émission obligatoire dès le 1ᵉʳ septembre 2027** (TPE/PME/auto-
   entrepreneurs) — a plain PDF by email will no longer satisfy the
   requirement; invoices must be transmitted as a structured file (Factur-X
   here). What to do: the "Facture électronique" button (or
   `autoAttachFacturX`, 1.3-2) produces the file; connecting SUPER PDP and
   using "Envoyer via PA" (or `autoTransmitViaPa`, 1.3-3) transmits it.
3. **"Faut-il vraiment passer par une plateforme tierce ?" — oui, ce n'est
   pas un choix de FactureLe.** The reform requires transmission through
   an agréée Plateforme (PA); the PPF (Portail Public de Facturation) has
   been a directory/data-concentrator only since 2024, not a transmission
   channel a business can use directly (verified during Phase 1.2-1's own
   PA research, not re-verified here — cross-reference, don't re-derive).
   SUPER PDP is FactureLe's integrated PA (Phase 1.2-1's decision) so this
   step is one connection, not a separate account to hunt down.
4. **Déclarations URSSAF : une obligation distincte, déjà couverte.** The
   reform doesn't change what's owed or declared to URSSAF — turnover is
   still self-declared from encaissements, same figures as before. That's
   Phase 17's existing Rapport Trimestriel (in "Statistiques"), unrelated
   to invoice *format* — explicitly named here only to stop an artisan
   from wondering if it's the same requirement as Factur-X/PA (it isn't).
5. **Honest disclosure: what FactureLe does *not* cover.** E-reporting
   (aggregate transaction data for B2C/export sales, distinct from
   e-invoicing itself) was a criterion checked while picking a PA
   (Phase 1.2-1's own comparison notes SUPER PDP supports it) but was
   never actually built as a FactureLe feature — only structured B2B
   invoicing (Factur-X emission/reception through the PA) is implemented.
   Worth surfacing explicitly for this app's own user base: an artisan
   invoicing individual homeowners has real B2C volume e-reporting could
   apply to. Matches this app's established "say plainly when we can't do
   X" principle (Phase 10/12/17) rather than letting the explainer imply
   full coverage by omission.

## "Met à jour le jour" — date-aware phrasing, not a static reminder

Read as: the explainer's own copy must stay temporally honest, not frozen
in future tense forever. Reuses Phase 1.2-6's existing
`daysUntil`/`E_INVOICING_RECEPTION_DEADLINE`/`E_INVOICING_EMISSION_DEADLINE`
(`core/utils/e-invoicing-deadlines.util.ts`) — same source of truth as the
deadline banners, never a second copy of the dates:

- Before a deadline: "obligatoire **à partir du** 1ᵉʳ septembre 2026".
- On/after it: "obligatoire **depuis le** 1ᵉʳ septembre 2026" — this
  matters concretely for reception, 8 days out as of this writing, which
  will cross into the past well within this track's own build window.

No visible "content last verified on [date]" note in the artisan-facing
UI itself (would read as an odd, internal/engineering-facing detail to an
end user) — the regulatory facts above (PPF's role, the PA requirement)
are dated and cross-referenced in this doc instead, for whoever maintains
this phase next.

## Non-goals

- No duplication of this content into Activity Analytics (1.3-6) — one
  place explains, the other confirms status; cross-linking from 1.3-6 to
  this disclosure is a reasonable future addition, not scoped in now (would
  need 1.3-6 to actually exist first, and doesn't need to ship together
  with it).
- No e-reporting implementation — this phase only *discloses* the gap
  honestly, it doesn't close it. Building e-reporting support, if ever
  justified, is a real future track of its own scale (comparable to Phase
  1.2 itself), not a bullet to fold in here.
- No "verified as of" timestamp visible to the artisan — see the dedicated
  section above.
