# Phase 1.3-5 — Non-Transmitted Reminders & Deadline Visibility

[← back to Phase 1.3 index](./README.md)

## Objective

Surfaces the two things the 2026-08-25 review flagged as easy to miss under
any mode: a FACTURE that's sat un-transmitted for a while, and how close the
reform's own deadlines actually are — without inventing new notification
machinery, by extending the digest push system
`push-notification/reminder-cron.service.ts` already ships.

## Checklist

### Backend

- [x] `push-notification/reminder-query.util.ts`: new
      `buildUnsentEInvoiceWhere(now)` — FACTUREs, `NOT_SENT`, `createdAt`
      more than 48h old, `company.superPdpConnectedAt: { not: null }` (a
      nested relation filter, not a second query) — same pure,
      unit-testable-without-Prisma shape as `buildLateInvoiceWhere`/
      `buildUnpaidNotLateInvoiceWhere`.
- [x] `push-notification.repository.ts`: `ReminderCounts` gained
      `unsentEInvoiceCount`; `findReminderCounts` now runs all three
      `groupBy` queries in the same `Promise.all` and merges into one Map
      via a small `empty(companyId)` helper (refactored slightly from the
      original two-bucket merge logic for the 3-way case, not just
      appended).
- [x] `reminder-cron.service.ts`: `buildDigestBody` takes
      `unsentEInvoiceCount` as a third, independent parameter — an invoice
      can be late/unpaid *and* un-transmitted at once, so this clause never
      suppresses in favor of the other two.
- [x] **`markReminded` extended, not left as-is**: confirmed the checklist's
      own hypothesis first (the count *is* recomputed fresh every run from
      live `eInvoiceTransmissionStatus`, `lastPushReminderAt` is written
      but genuinely never read back by any query — grepped to confirm, not
      assumed), so a transmitted invoice already naturally stops counting
      with zero changes needed there. Still extended `markReminded`'s own
      `WHERE` with an `OR` (`status: 'NON_PAYEE'` OR
      `{ documentType: 'FACTURE', eInvoiceTransmissionStatus: 'NOT_SENT' }`)
      so the field's own documented meaning ("the artisan was already
      push-notified about this invoice today") stays true for all three
      reminder types it can now represent, not just the original two —
      even though nothing currently reads it as a suppression check, a
      future maintainer reasonably might.

### Frontend

- [x] New `shared/components/deadline-banner.component.ts` (+ `.html`) —

- [x] Added to `invoice-board.page.html`, right under the "Mes documents"

- [x] Dismiss state in `localStorage`, keyed

- [x] **No component-level unit test written** — confirmed this

      existing frontend spec files are all utils/stores/services), so a
      new one here would be a new testing pattern, not a continuation of

## Non-goals

- No separate opt-in toggle for the reminder bucket — it rides the same
  push-notification opt-in every other digest bucket already uses
  (registering a device token in the first place), consistent with
  "customizable" meaning real choices, not one more thing to configure for
  what's really just an added line in an existing digest.

## Notes

- Depends on [1.3-3](./1.3-3-delayed-auto-transmit.md) (most useful once
  auto-transmit exists as an alternative — under pure-manual mode this
  bucket still fires correctly for a FACTURE the artisan simply hasn't
  gotten to yet, which is exactly its intended use either way).
- The deadline banner's dismiss state needs *some* persistence —
  localStorage is the natural fit (a per-viewer UI preference, not data
  another session needs to see), not a new DB column, matching this app's
  existing "browser storage for viewer conveniences" precedent.
