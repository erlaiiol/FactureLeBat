# Phase 1.3-3 — Delayed Automatic PA Transmission

[← back to Phase 1.3 index](./README.md)

## Objective

The main "set it and forget it" piece: with `autoTransmitViaPa` on, a
newly-created FACTURE is queued for transmission and sent to the connected
PA on its own. Per the 2026-08-25 scope decision, not instantly —
transmission happens after a short, fixed grace period during which the
artisan can still cancel it from the invoice board, closing the gap an
instant auto-send would leave (zero time to catch a mistake before it
reaches a third party/the tax administration's channel).

## Data Model

- `Invoice.scheduledTransmitAt DateTime?` — set at FACTURE creation when
  `autoTransmitViaPa` is on; null means "not queued" (manual mode, a DEVIS,
  or already sent/cancelled).
- `Invoice.transmitCancelledAt DateTime?` — set when the artisan cancels a
  still-pending auto-transmission; the sweep skips any row where this is
  set.
- A `@Cron`-scheduled sweep (same `@nestjs/schedule` pattern
  `ReminderCronService` already established as "first scheduled job in this
  codebase," running in-process on this app's single backend instance)
  finds FACTUREs whose `scheduledTransmitAt` has passed and
  `transmitCancelledAt` is still null, and calls
  `EInvoiceTransmissionService.transmit` unchanged. A DB-persisted "due at"
  timestamp plus a periodic sweep is deliberately chosen over a per-invoice
  in-memory timer (e.g. `setTimeout`), which wouldn't survive a redeploy —
  this needs to still fire correctly even if the backend restarts
  mid-grace-period.

**Real gap found and closed while implementing this phase — not in the
original plan**: nothing prevented the exact same invoice from being
transmitted twice if a manual "Envoyer via PA" click raced the new cron
sweep (or two overlapping cron ticks raced each other). Closed with two
layered defenses:
1. `InvoiceRepository.claimAutoTransmit` atomically nulls
   `scheduledTransmitAt` gated on it still being set — the cron sweep must
   successfully claim a row (an `updateMany` whose `count` confirms
   exclusivity) before calling `transmit()`; a second concurrent claim
   attempt on the same row gets `count: 0` and skips it.
2. `EInvoiceTransmissionService.transmit` itself now throws
   `ConflictException` unless `eInvoiceTransmissionStatus` is still
   `NOT_SENT`/`REJECTED` — a backend-level backstop mirroring the
   frontend's own `canTransmit()` gate, closing the residual window where a
   manual click and the cron's claim happen close enough together that
   claiming alone wouldn't have caught it.

Deliberately **not** added: a new `SENDING`/in-flight status value, which
would fully close the last few milliseconds of that window but meant
touching the already-shipped, already-tested `EInvoiceTransmissionStatus`
vocabulary across backend and frontend for a residual race narrow enough
(sub-second, requires an artisan clicking the exact row within the exact
window the cron is mid-flight on it) that the cost wasn't proportionate.

## Non-goals

- No per-company configurable grace-period duration — one fixed value for
  everyone who opts in.
- No retry/backoff scheduling for a failed auto-transmission — it lands
  back in the same `NOT_SENT` state a failed manual click would, picked up
  by [1.3-5](./1.3-5-reminders-deadline-visibility.md)'s digest rather than
  silently retried in the background.

- Depends on [1.3-1](./1.3-1-workflow-preferences.md) (the toggle) and

  own "resubmit as a new PA-side invoice" flow) stays immediate and
  artisan-initiated, same as today.
