# Phase 1.3-6 — E-Invoicing Metrics in Activity Analytics

[← back to Phase 1.3 index](./README.md)

## Objective

Flagged directly by the user (2026-08-25): the e-invoicing pipeline's own
health needs to stay visible in "Mon activité" (Phase 17's Activity
Analytics), this app's one existing place for "how's my business doing" at
a glance — not just surfaced reactively via a reminder push
([1.3-5](./1.3-5-reminders-deadline-visibility.md)) or left to a settings
page (1.2-6) nobody revisits once they've connected. As 1.3-3/1.3-4 make
transmission and reception happen without a click, this becomes the place
that keeps confirming the automation is actually doing its job, not just
trust running quietly in the background.

## Correction vs. the original plan (found while writing this checklist)

The original draft of this phase (in `docs/roadmap.md`) said "no premium
gate, matches Phase 17's own decision that Activity Analytics is always
reachable." **That's stale — Phase 30 (`docs/roadmap.md`) gated
`GET /reports/analytics` behind `PlanGateService.assertFeatureAccess(...,
'analytics')` after Phase 17 originally shipped**, specifically because the
user confirmed pure business-insight analytics was fair game to paywall
("on peut légiférer sur les statistiques"), while `GET /reports/quarterly`
(the URSSAF declaration) stays free everywhere because it's a legal
necessity, not a nice-to-have.

An e-invoicing compliance snapshot (am I connected, is my transmission rate
healthy) reads much closer to "legal necessity" than "business insight" —
an artisan needs to know their own reform-compliance status regardless of
subscription tier, same reasoning that keeps the quarterly report free.
**So this phase must not simply inherit Activity Analytics' existing gate.**
The compliance snapshot card needs its own ungated surface, even though it
sits visually next to the (gated) rest of the dashboard.

## Checklist

### Backend

- [x] New `ReportsService.getEInvoicingSnapshot(companyId)` — a separate
      method from `getActivityAnalytics`, **never calls
      `assertFeatureAccess`** (confirmed by a dedicated unit test, not
      just by reading the code). Computes: `configured`/`connected`
      (`CompanySuperPdpService`), `facturesInWindow`/
      `transmittedFacturesInWindow`/`transmissionRatePercent` (rounded,
      `null` not `0` when the denominator is 0) over the same
      `ANALYTICS_WINDOW_MONTHS` window, `unsentFactureCount`
      (deliberately whole-book, not windowed — same "legal-risk count"
      treatment as `unsignedFactureCount`), `receivedInvoiceCount`
      (windowed, count only).
- [x] New endpoint `GET /reports/e-invoicing-snapshot`, ungated, alongside
      `GET /reports/analytics`.
- [x] `ReportsController`'s class comment extended — now describes three
      cases (quarterly free / analytics gated / this endpoint also free),
      not two. Also extended Phase 30's own section in `docs/roadmap.md`
      with the same update, cross-referenced both ways.
- [x] **Two repository additions the original plan didn't call out by
      name**: `InvoiceRepository.countFacturesInRange`/
      `countTransmittedFacturesInRange`/`countUnsentFactures` (three new
      plain counts, mirroring `countUnsigned`'s existing shape) and
      `ReceivedInvoiceRepository.countInRange` (windowed by `receivedAt`,
      never `issueDate` — SUPER PDP doesn't always supply the latter).
- [x] **Module wiring**: `ReceivedInvoiceRepository` wasn't exported from
      `ReceivedInvoiceModule` at all before this phase — added
      `exports: [ReceivedInvoiceRepository]` there and imported
      `ReceivedInvoiceModule` into `ReportsModule`. Checked for a
      circular-dependency risk first (`ReceivedInvoiceModule` imports
      `InvoiceModule`/`CompanyModule`, neither of which imports
      `ReportsModule`) rather than assuming it was safe.

### Frontend

- [x] `core/services/reports.service.ts`:
      `getEInvoicingSnapshot(): Observable<EInvoicingSnapshot>`.
- [x] Rendered in `stats-reports.page.html` **before** (not just outside)
      the `analyticsLoading()`/`analyticsLocked()`/`analyticsError()`/
      `analytics()` chain — the compliance card is the first thing on the
      "Vue d'ensemble" tab, not an afterthought below a paywall card.
- [x] Card contents: transmission rate (plain number + `%`, no new chart
      component), un-transmitted count, received-invoice count with
      "Ces factures n'alimentent pas vos rapports d'activité." — the
      **exact verbatim phrase** already used on the reception inbox page
      (`received-invoice-list.page.html`), grepped for and copied, not
      retyped from memory.
- [x] Two honest non-zero states, not one: `!configured` ("pas encore
      configurée sur ce déploiement") is a **different** message from
      `!connected` ("Connectez SUPER PDP depuis Mon entreprise", linking
      there) — a deployment with no SUPER PDP credentials at all and an
      artisan who just hasn't connected yet are different situations, and
      conflating them into one generic message would have been less
      honest than the two-branch version this phase actually shipped.

### Tests

- [x] Backend: 5 new tests in `reports.service.spec.ts` —
      `getEInvoicingSnapshot` never calls `assertFeatureAccess`
      (the load-bearing proof of "ungated," not just an assumption),
      correct rounded rate from a connected company with mixed statuses,
      `null` (not `0`) rate with zero FACTUREs in window, unsent/received
      counts pass through untouched, `configured`/`connected` reported
      independently.
- [x] **Not written as a request-level 402 test** — this codebase's
      billing-gate tests live at the service-unit level (asserting
      `assertFeatureAccess` was/wasn't called), not as HTTP-layer request
      tests; matched that existing convention instead of introducing a new
      one for just this endpoint.
- [x] **No frontend component test** — same established precedent as
      1.3-3/1.3-4/1.3-5 (zero Angular `TestBed` specs anywhere in this
      codebase). Verified live instead (below), including the specific
      scenario the checklist called out by name: a company whose plan
      tier genuinely locks `analytics`.

**Live verification (2026-08-24)**: backend rebuilt, booted clean with the
new `ReceivedInvoiceModule` import and endpoint registered. On
"Statistiques": the compliance card renders correctly showing "Cette
fonctionnalité n'est pas encore configurée..." (this deployment has no
SUPER PDP credentials at all, so `configured: false` is the honest,
correct state here — confirmed this is the right branch, not a bug, by
checking `isConfigured()`'s own env-var check). **The specific case this
checklist called out**: temporarily nulled a demo company's
`grantedPlanTier` via `psql` to genuinely trigger `PlanFeatureLocked` on
`analytics` — screenshotted the result: the compliance card still renders
in full, completely above and independent of the "Les statistiques
d'activité sont réservées aux offres Pro et Premium" upsell card right
below it. Reverted immediately after. The `connected: true` branch (real
transmission-rate numbers rendering) could not be exercised live — no
real `SUPERPDP_CLIENT_ID`/`SECRET` exist in this environment, same
limitation as every other 1.2/1.3 phase touching SUPER PDP — relied on
`tsc`'s strict template type-checking (which would catch a bad property
access on `EInvoicingSnapshot`) plus the backend unit tests' own full
coverage of that computation instead.

## Non-goals

- **Still no expense/revenue treatment of received invoices.** This is an
  operational/compliance metric, not a financial one — doesn't reverse
  Phase 1.2-5's own "no accounting features off the back of reception"
  non-goal, which this phase's own received-count call-out exists
  specifically to keep honest.
- **No premium gate** — see the correction above; this is the one deviation
  from this phase's original draft.

## Notes

- Depends on Phase 1.2-4 (transmission status) and 1.2-5 (reception) for
  the underlying data; benefits from 1.3-3/1.3-4 existing to explain *why*
  the numbers move without a manual click, but doesn't require them — the
  snapshot is just as meaningful under pure-manual mode.
- Extends "Mon activité" rather than a new screen, the same precedent
  Phase 17 itself set when it was added to Phase 9's existing settings
  section instead of a dedicated page — but as a sibling section with its
  own gating, not folded into `getActivityAnalytics` itself.
